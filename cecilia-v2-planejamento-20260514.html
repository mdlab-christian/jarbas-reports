Por que v1–v7 nunca funcionou

Seção 01
⚠ Situação atual: 26 intimações no banco. 100% com movimento_em_duvida. Budget de $2 cortava 88% das análises. Pipeline S0-S9 quebrava por contrato rígido entre stages.
P0-01 · Crítico
Pipeline S0-S9 com contrato rígido
419 intimações com classe_cecilia=null. Cada stage esperava output exato do anterior — qualquer variação no EPROC quebrava toda a cadeia silenciosamente.
V2: SDK Agent elimina pipeline rígido. Agente decide fluxo dinamicamente com tools.
P0-02 · Crítico
SP535101 TJSP completamente parado
TJSP usa e-SAJ, não EPROC. Tentativas de login falhavam silenciosamente. Nenhum processo paulista foi monitorado desde o início do projeto.
V2: Módulo e-SAJ separado em fase 3. Focar TJRS/TJSC na v2 — 4 OABs funcionais.
P0-03 · Crítico
Centenas de erros/hora na config fetch
Worker buscava configurações do banco a cada ciclo. Erros em cascata geravam noise nos logs e interrompiam processamento legítimo sem alerta claro.
V2: Defaults hardcoded no worker. Zero fetch de config em tempo de execução.
P0-04 · Crítico
Budget $2 cortava análise — 12% de completion
Sonnet em todos os passos consumia budget rapidamente. 88% das análises nunca completavam. Sistema estatisticamente inútil para tomada de decisão.
V2: Haiku na triagem (~$0,40/mês). Sonnet só para intimações relevantes (~20% do volume).
P0-05 · Crítico
Conteúdo de PDFs nunca carregava (S5)
Stage S5 tentava extrair PDFs renderizados dinamicamente. EPROC serve conteúdo via sessão autenticada — sem cache de URL, o conteúdo ficava inacessível após primeira visita.
V2: Descoberta-chave — URLs acessar_documento contêm 15K–64K chars. São permanentes. Cache = ouro.
P1-01 · Alta prioridade
1.468 intimações pendentes sem re-queue
Intimações que falharam nunca voltaram para a fila. Backlog crescendo silenciosamente sem alerta para a equipe.
V2: Backfill job na semana 1. Reset de todas pendentes para re-análise.
P1-02 · Alta prioridade
Circuit breaker agressivo (3 falhas → 24h pause)
3 falhas consecutivas travavam o sistema por 24 horas inteiras. Uma instabilidade pontual de rede pausava o dia completo de monitoramento.
V2: Threshold 5 falhas. Reset automático em 4h. Notificação Telegram ao travar.
P1-03 · Alta prioridade
RAG com 125 registros inválidos
Bug no GOOGLE_AI_API_KEY gerou vetores corrompidos na base de busca semântica. Similaridade comprometida em todas as consultas de contexto.
V2: Fix na key + reprocessamento completo do RAG pré-produção.
P2-01 · Estrutural
Polo oposto invisível no EPROC
EPROC mostra apenas o polo do advogado logado. Réus/autores do lado oposto ficam ocultos — análise incompleta por design da plataforma.
V2: Página pública do processo (sem login) para capturar ambos os polos via scraping.
P2-02 · Estrutural
Judit API — attachments TJRS sempre vazios
Testado ao vivo: TJRS retorna consistentemente attachments: []. R$7.637/mês por uma API que não entrega o conteúdo que o sistema precisava.
V2: Judit descartada para conteúdo. Decisão D9 define se vale usar para marco zero estruturado.

Seção 04
📌 Instrução: Responda D1=A/B/C para cada decisão. Após confirmar todas as 12, o próximo Claude gera a spec.md e inicia investigações paralelas com subagentes. O prompt de retomada está na Seção 07.
D1
Agente de Navegação: qual tecnologia usar?
REC → A
A navegação no EPROC exige TOTP, sessões persistentes e interação com elementos dinâmicos. A escolha impacta custo, confiabilidade e velocidade de desenvolvimento. Playwright já está provado com as 5 OABs no Mac Mini (user cecilia, UID 506).
A
Playwright (Node.js)
Tecnologia comprovada. Login + TOTP funcional com 4 OABs EPROC. Rodando no Mac Mini. Manutenção conhecida. Zero custo adicional de API. PB6 (playbook navegação) já existe para adaptar.
REC
B
OpenClaw + Ollama local
Sem custo de API para visão. Modelo local no Mac Mini. Requer instalação do Ollama + modelo de visão (LLaVA ou similar). Menos testado para navegação no EPROC especificamente.
C
Playwright + Claude Vision (screenshots)
Mais robusto para mudanças de layout. Cada screenshot adiciona custo de API (Sonnet). Para páginas com layouts variáveis pode ser mais preciso que seletores CSS fixos.
D2
thread_id — Histórico contínuo por processo
REC → B
O SDK Agent precisa de memória persistente por processo. Cada CNJ deve ter histórico acumulado de análises anteriores para o agente evoluir com o tempo e não repetir trabalho já feito. Decisão crítica de arquitetura — sem volta fácil.
A
OpenAI Assistants API
Thread nativo e gerenciado pela OpenAI. Sem preocupação com armazenamento. Porém: lock-in OpenAI, GPT-4o inferior ao Sonnet em jurídico pt-BR, custo adicional por thread ativo.
B
Claude Sonnet + tabela Supabase
Tabela cecilia_thread_messages no Supabase. Thread simulado injetado no system prompt. Sem lock-in. Sonnet 4.6 superior em jurídico pt-BR. Histórico consultável via SQL. Integra com stack existente.
REC
C
Arquivo Obsidian como único histórico
Mais simples. Arquivo Markdown é o estado completo. Sem tabela adicional. Limitação: consultas complexas impossíveis, sem queries SQL, sem agregações de performance.
D3
Marco zero: histórico completo dos 8.485 processos
REC → C
8.485 processos Midas sem histórico no sistema novo. Precisa decidir: pagar para ter tudo de uma vez, baixar gradualmente via EPROC, ou começar do zero e acumular via XLS diário.
A
Judit — GET /lawsuits/{cnj}/{instance}
Dados estruturados instantâneos: partes, juiz, vara, datas, movimentos. Porém: attachments TJRS = [] comprovado. Histórico de texto funciona. Custo estimado: R$1.500–R$4.000 one-time para 8.485 processos.
B
EPROC "Download Completo" — scraping gradual
Gratuito. Playwright baixa íntegra de cada processo. Lento (~5 min por processo). 8.485 processos = semanas de processamento em background. Viável como processo assíncrono paralelo à operação normal.
C
Sem marco zero — XLS diário como base
Começa do zero. O XLS diário constrói o histórico naturalmente. Para processos críticos urgentes: navegação manual pontual. Zero custo imediato. Menos complexidade no lançamento da v2.
REC
D4
Paralelismo da fila de processamento
REC → A
Paralelismo aumenta velocidade mas aumenta risco de bloqueio no EPROC. TJRS detecta comportamento anômalo. Sessões simultâneas com a mesma OAB podem ser recusadas ou gerar CAPTCHA.
A
Sequencial — um processo por vez
Mais seguro. Zero risco de bloqueio. Comprovado funcional. Para 50–200 processos diários: ~2–5h de processamento noturno. Aceitável com agendamento após expediente.
REC
B
Pool de 3 paralelos com p-limit
3x mais rápido. Risco moderado de bloqueio por IP/sessão. Requer rotação de OABs por slot. Mais complexo de implementar, debugar e monitorar.
C
Sequencial com timeout 60s por processo
Como A mas com timeout forçado por processo. Evita travar em processo problemático. Desvantagem: corte arbitrário pode interromper análises legítimas de documentos longos.
D5
Estrutura de diretórios no vault Obsidian
REC → B
A hierarquia do Obsidian define como a equipe navega e como o agente lê contexto. Deve refletir divisão geográfica ou jurisdicional. Afeta busca, links internos e legibilidade humana direta.
A
Estado / Vara / CNJ.md
Ex: RS/2CIV2-CAN/0001234-56.2024.8.21.0001.md. Agrupa por vara — útil para análise de padrão por vara específica. Código de vara não é intuitivo para navegação humana.
B
Estado / Comarca / CNJ.md
Ex: RS/Canoas/0001234-56.2024.8.21.0001.md. Legível para humanos. Fácil de navegar no Obsidian. Comarca é como a equipe pensa geograficamente sobre o portfólio.
REC
C
Estado / Juiz / CNJ.md
Agrupa por magistrado — ideal para jurimetria de perfil de juiz. Problema: juízes são transferidos entre varas. Hierarquia se torna instável ao longo do tempo processual.
D6
Worker B de triagem: manter ou remover?
REC → A
O custo do Sonnet é o maior gargalo do sistema. Worker B filtra intimações irrelevantes antes de passar para análise profunda. A questão é se o custo do Haiku na triagem se justifica pela economia gerada no Sonnet.
A
Manter haiku-4.5 (~$0,40/mês)
Triagem barata. Estimativa: 70–80% dos eventos EPROC são despachos de rotina (juntada, certidão, conclusos). Haiku filtra esses. Sonnet só analisa o que realmente importa. ROI claro e mensurável.
REC
B
Remover — tudo direto para Worker C
Menor complexidade arquitetural. Sonnet analisa todos os eventos. Custo maior por volume mas fluxo mais simples. Sonnet tem contexto histórico do CNJ e pode identificar ruído sozinho.
C
Regras simples — keywords sem IA
Lista de termos que indicam ruído: "Juntada de documento", "Certidão", "Conclusos aos autos". Custo zero. Limitação: falsos negativos em intimações com linguagem incomum ou combinada.
D7
TJSP e-SAJ: incluir no escopo da v2?
REC → B
SP535101 (OAB/SP Christian) monitora processos no TJSP, que usa o sistema e-SAJ — completamente diferente do EPROC em login, sessões e estrutura HTML. Implementar os dois em paralelo aumenta escopo e risco de atraso na v2.
A
Incluir TJSP na v2 (módulo e-SAJ)
Resolve SP535101 imediatamente. Adiciona ~40% de esforço ao escopo da v2. Dois sistemas completamente diferentes em paralelo. Alto risco de atrasar entrega do núcleo funcional EPROC.
B
Excluir TJSP — módulo separado na v3
Foco total no núcleo EPROC (RS116571 · RS131163 · SC074025 · SC075466). Com o núcleo provado em produção, módulo e-SAJ vira um adapter isolado de menor risco. SP535101 continua manual na v2.

Frontend: nova rota /cecilia ou tab no /controller?
REC → A
O painel Cecília (upload XLS, fila, concluídos, status dos workers) precisa de uma casa no frontend. O drawer do /controller já tem aba "OlivIA" que pode ser renomeada. Drawer já existe e é familiar para a equipe jurídica.

Tab "Cecília Monitor" no /controller
Aproveita contexto de controller (processos, intimações). Renomeia aba "OlivIA" para "Cecília". Drawer já existe e é familiar para a equipe. Zero nova rota para aprender. Menor esforço frontend.

B
Nova rota /cecilia separada
Dashboard dedicado com mais espaço para visualizações (timeline de fila, métricas históricas, logs). Curva de navegação da equipe — nova URL para aprender e adotar.

Painel colapsável no /controller (header)
Banner no topo do controller: último upload, fila ativa, alertas. Expande ao clicar. Presente em todas as visualizações do controller. Menos invasivo no layout atual.
D9
Judit para marco zero: usar ou não?
REC → B
Judit oferece dados estruturados de processos via API. Testado ao vivo: attachments TJRS retornam sempre vazios. Histórico de movimentos funciona. Questão: vale pagar para ter metadados de 8.485 processos em um batch único?
A
Usar Judit para marco zero (batch one-time)
Dados estruturados instantâneos: partes, juiz, vara, datas, histórico de movimentos. Sem conteúdo de PDF — mas metadados completos. Custo estimado: R$1.500–R$4.000 para 8.485 processos.
B
Não usar Judit — tudo via EPROC direto
Zero custo adicional. XLS diário constrói a base gradualmente. Para processos prioritários: navegação manual pontual via Worker A. A v1 pagou R$7.637/mês por uma API que não entregava conteúdo.
REC
D10
Onde persistir thread_store — histórico por CNJ?
REC → A
O SDK Agent injeta histórico de análises anteriores no context window a cada nova análise do mesmo processo. Precisa ser consultável, persistente entre sessões e com controle de tamanho por token count.
A
Tabela cecilia_thread_messages
Supabase. Rows: thread_id (=CNJ), role (system/user/assistant), content, created_at. Consultável via SQL. RLS por organizacao_id. Persistente, auditável, truncável por token count. Integra com stack.
REC
B
Campo JSONB processos.cecilia_thread
Sem nova tabela. Thread armazenado direto em processos. Limitação: JSONB cresce indefinidamente, difícil de truncar por token count, UPDATE em tabela grande a cada análise.
C
Obsidian como único histórico
Markdown simples. Sem SQL. O worker Node.js leria arquivos via fs — possível mas frágil. Difícil agregar ou consultar programaticamente. Obsidian Sync pode gerar conflitos de escrita.
D11
Quando Cecília atualiza o arquivo Obsidian?
REC → C
Cada análise pode ou não justificar uma atualização no vault Obsidian. Atualizar após cada evento gera I/O constante e pode travar o Obsidian Sync entre Mac Mini, Pro e Air. Batch é mais eficiente mas perde urgência.
A
Após cada análise — tempo real
Arquivo sempre atualizado. Alto I/O no vault. Para 200 processos/dia: 200 writes em série. Pode conflitar com Obsidian Sync entre Mac Mini e MacBook Pro durante o expediente.
B
Uma vez por dia — batch noturno
I/O concentrado em ciclo único. Arquivo defasado por até 24h. Mais eficiente para o Obsidian Sync. Adequado se a equipe não consulta o vault durante o processamento.
C
Somente para intimações relevantes
Worker B classificou como relevante? Atualiza Obsidian. Ruído? Sem write. Reduz I/O em ~75%. O vault Obsidian reflete apenas o que importa para a equipe. Balanceado entre frequência e relevância.

Superior em jurídico pt-BR — comprovado em OlivIA com resultados excelentes. Thread simulado via tabela Supabase — sem lock-in. SDK Agent com tools. Modelo padrão do stack MDFlow. Sem surpresas de integração.
