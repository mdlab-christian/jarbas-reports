Veredito Rapido

SECAO 1
Cecilia v8 via EPROC + Playwright e viavel, mais barata e potencialmente mais eficaz que a Judit.

Apos testes ao vivo, a Datajud API retornou "Nao encontrado" para todos os processos TJRS. A Judit, com custo de R$7.637/mes, entregou attachments sempre vazios para TJRS e media de 164 chars por evento — inutilizavel para analise juridica real.

O caminho escolhido e o sistema proprio: EPROC + Playwright, com arquitetura de 5 workers especializados, Worker C como SDK agent e URL caching agressivo de URLs acessar_documento.

  • 1. URLs acessar_documento do EPROC tem 15.593 a 63.701 chars de conteudo real — 100 vezes mais que a Judit entregou para TJRS (164 chars medios)
  • 2. Datajud testado ao vivo e descartado: API nao retornou nenhum processo TJRS; lag confirmado de 15 dias torna a fonte inutilizavel para monitoramento em tempo real
  • 3. O sistema ja tem 70% da infraestrutura construida: Workers B/C funcionais, tabelas, playbooks PB1–PB7, Mac Mini, crons, LaunchDaemons — so falta otimizar a camada de discovery

Inventario Completo de Problemas

SECAO 2
13 problemas documentados — 5 P0 criticos, 5 P1 esta semana, 3 P2 estruturais. Cada problema inclui causa raiz, impacto medido e solucao v8 especifica.

🔴 P0 — Criticos (bloqueiam funcionamento)

P0 P0-01 68.2% movimento_em_duvida — problema raiz historico
v6 68.2% duvida v7 Judit 100% duvida (pior) Impacto analise cega Escopo todos tribunais
Causa Raiz
EPROC mostra apenas eventos do polo onde o advogado esta logado. Eventos do polo oposto — audiencia marcada pela parte contraria, decisao sem intimacao direta — sao completamente invisiveis para a sessao autenticada.
Solucao v8: Portal Publico TJRS (sem login, ve ambos os polos) via Worker A3 + caching agressivo de URLs acessar_documento para documentos ja descobertos. Worker A v2 (rapido, 5 paginas/sessao) + Worker A3 (completo, ambos polos) cobre 100% dos eventos relevantes.
P0 P0-02 SP535101 (TJSP) completamente parado
Impacto 1.250+ processos SP Causa TJSP usa e-SAJ, nao EPROC Status zero monitoramento
Causa Raiz
TJSP utiliza o sistema e-SAJ (Softplan), enquanto TJRS e TJSC utilizam EPROC. Login diferente, XLS de importacao diferente, estrutura de navegacao completamente diferente. O Worker A v2 foi construido para EPROC e nao funciona com e-SAJ.
Solucao v8: Modulo tjsp_esaj_module.mjs separado — navegacao especifica para e-SAJ, login Christian/SP535101, extracao de movimentacoes pelo portal publico eSAJ TJSP quando possivel. Semana 5 do plano de implementacao.
P0 P0-03 S5 conteudo vazio frequente — Claude analisa sem documento
Causa PDF nao renderiza / popup / timeout Resultado movimento_em_duvida Frequencia alta
Causa Raiz
O stage S5 usa Playwright para capturar conteudo do documento. Quando o PDF nao renderiza dentro do iframe, popup bloqueia, ou timeout expira, o campo documento_raw fica vazio. Claude recebe apenas o titulo do evento e classifica como movimento_em_duvida.
Solucao v8: URL caching elimina o problema para documentos ja conhecidos: acessar_documento cacheada = fetch HTTP direto, sem Playwright, sem risco de iframe/popup/timeout. Para URLs nao cacheadas, o Worker C SDK agent pode dinamicamente tentar novamente com estrategia diferente.
P0 P0-04 Budget $2/OAB insuficiente — RS116571 analisou so 12% dos processos
OAB afetada RS116571 (principal) Processos 1.105 com movimento Analisados 130 (12%) Budget $2 hardcoded
Causa Raiz
Budget hardcoded de $2 por OAB limita severamente o numero de analises com Sonnet. A OAB com mais processos ativos (RS116571) atingia o limite antes de processar a maioria dos eventos novos, deixando 88% das intimacoes sem analise.
Solucao v8: Remover budget cap. Usar haiku-4.5 no Worker B para triagem (95% mais barato que Sonnet). Custo real estimado: 8.485 processos x 50 tokens medios x 3x/dia = 425K tokens/dia = $0.11/dia ($3.30/mes). Sonnet reservado apenas para analise final no Worker C.
P0 P0-05 S6→S7 analise_ia ausente — 419 phantom intimacoes
Afetados 419 registros Estado classe_cecilia=null + ia_status=concluido Causa campo classe name drift
Causa Raiz
O campo classe tem nome diferente do esperado pelo parser do S7, ou o JSON retornado pelo Claude tem chave diferente da esperada. Stage S6 roda com sucesso mas S7 nao encontra o campo e salva analise_ia=null. ia_status fica "concluido" sem dados — phantom intimacoes.
Solucao v8: Worker C como SDK agent elimina o contrato rigido S6→S7. O agent retorna estrutura validada pela RPC fn_intimacao_insert_validated — sem parsing fragil, com validacao no banco. Para os 419 registros existentes: job de backfill com re-analise.

🟡 P1 — Esta Semana

P1 P1-01 1.468 intimacoes pendentes nunca analisadas
Volume 1.468 registros Estado ia_status=pendente Causa re-queue nao implementado
Solucao: Backfill job unico (1x execucao via cron manual) + re-queue automatico para ia_status=pendente com mais de 24h sem processamento. Prioridade por data descendente.
P1 P1-02 Circuit breaker RS116571 muito agressivo — pausa 24h na OAB principal
OAB RS116571 (1.150+ processos) Threshold atual 3 falhas → pausa 24h Impacto downtime completo na OAB principal
Solucao: Threshold 5 falhas consecutivas, reset em 4h (nao 24h). Alarme Telegram quando circuit breaker ativar.
P1 P1-03 Config fetch error — centenas de erros por hora nos logs
Causa Endpoint config dinamica inacessivel Impacto logs poluidos, dificulta diagnostico real
Solucao: Hardcode dos defaults de configuracao + retry silencioso com exponential backoff. Remover endpoint externo ou migrar para variavel de ambiente.
P1 P1-04 RAG com 125 registros invalidos — GOOGLE_AI_API_KEY incorreta
Registros invalidos 125 Causa bug em env var GOOGLE_AI_API_KEY Resultado few-shot dinamico desativado
Solucao: Corrigir env var GOOGLE_AI_API_KEY no LaunchDaemon + reprocessar 125 registros. RAG ativo significa Worker C recebe exemplos de casos similares para cada analise.
P1 P1-05 Dois controller-agents (PROD + DEV) com risco de colisao
PROD /Users/cecilia/Documents/... DEV /Users/jarbas/controller-agent/ Risco double-write no banco
Solucao: Renomear DEV para dev-controller-agent + bloquear LaunchAgent do DEV. Nunca dois agents ativos simultaneos no mesmo Supabase.

Solucao v8: Worker C SDK agent atualiza cecilia_feedback automaticamente quando Joao valida uma analise. Feedback loop ativo melhora RAG progressivamente.

TJSC layout diferente do TJRS TJSP e-SAJ completamente diferente
Solucao v8: Modulos tribunal-especificos: tjrs_module.mjs, tjsc_module.mjs, tjsp_esaj_module.mjs. Cada modulo tem seletores CSS, logica de login e extracao de movimentacoes proprios.

Arquitetura Cecilia v8 — Sistema Completo

SECAO 3
5 principios da v8: EPROC first · URL caching agressivo · 5 paginas cobrem tudo (1 por OAB) · Worker C = SDK agent · Tri-tier de modelos: haiku-4.5 → o4-mini → claude-sonnet-4-6
Worker A v2 — Smart Discovery
3x/dia: 6h, 13h, 19h · Script Node.js otimizado · NAO SDK agent
Node.js
1.
Login EPROC para cada OAB — 5 sessoes em paralelo. TOTP ja implementado via otplib.
2.
Navega "Ultimas Movimentacoes" → 1 unica pagina por OAB cobre todos os processos ativos. 5 OABs = 5 requests totais. Altamente eficiente.
3.
Extrai por evento: cnj · evento_id · data · tipo_evento · descricao_curta
4a.
Para cada evento novo (evento_id > ultimo_evento_id) com palavras-chave relevantes (sentenca, decisao, despacho): navega ao processo, extrai URL acessar_documento → INSERT cecilia_processo_urls (cache permanente)
4b.
INSERT cecilia_movimentacoes_brutas: fonte='eproc', documento_url, documento_raw=null, evento_polo detectado pela OAB (ativa=autor, passiva=reu)
5.
UPDATE processos.ultimo_evento_id + ultima_movimentacao_em. Saida: INSERT jobs fase='B'
Worker A3 — Portal Publico Discovery
1x/dia: 04h · Resolve polo oposto (P0-01 + P2-01) · NAO substitui Worker A v2
NOVO
1.
Acessa https://consultas.tjrs.jus.br/consulta/processo SEM LOGIN — ve ambos os polos do processo
2.
Escopo restrito: apenas processos com movimentacao nas ultimas 72h (detectada pelo Worker A v2). Nao varre todos os 8.485 ativos — otimizacao critica de volume.
3.
Compara eventos com ultimo_evento_id. Eventos novos do polo oposto → INSERT cecilia_movimentacoes_brutas com fonte='eproc_public'
!
Worker A v2 e rapido (5 requests totais). Worker A3 e mais lento (N processos por Playwright) mas roda 1x/dia apenas em processos com movimento recente. Complementar, nao substituto.

On-demand · Ativado pelo Worker B · Elimina P0-03 em definitivo

Cecilia como SDK Agent — Vale a Pena?

SECAO 4
Sim — mas apenas para o Worker C
  • ✅ Elimina BUG-P0-05 (analise_ia ausente): agent nao tem contratos rigidos entre stages — retorna estrutura validada pela RPC, sem parsing fragil S6→S7
  • ✅ Elimina BUG-P0-03 (content vazio): agent decide dinamicamente buscar mais conteudo quando documento_raw esta insuficiente — tool use real com raciocinio
  • ✅ Ativa RAG naturalmente: tool use para buscar casos similares via search_similar_cases — substitui few-shot estatico por recuperacao dinamica
  • ✅ Joao pode auditar o raciocinio: cada step_thinking fica logado em cecilia_feedback — auditavel, exportavel, treinavel por Joao
  • ✅ Melhora com feedback: agent consulta intimacoes passadas similares (RAG) — quanto mais Joao valida, mais precisa fica a analise juridica
Nao para Workers A e B — overhead nao justificado
Worker A v2: Script Node.js otimizado. Varrer 1 pagina por OAB = 5 requests simples. SDK agent teria overhead de multiplos round-trips de API para tarefa trivial. Com 8.485 processos x SDK agent = custo proibitivo.

Worker B: haiku-4.5 direto (mensagem unica). Triagem leve nao justifica raciocinio multi-step.

Workers A3 e A4: Scripts Node.js otimizados. Tarefas deterministicas: navegar portal publico, fazer fetch HTTP. Sem raciocinio dinamico necessario.
