interface LeadFilters {

  tempo_sem_resposta: string | null                 // ?tempo=

}

Realtime e Cache

useCrmRealtime — 2 Canais

Canal 1 — crm-channel-events-realtime

Tabela: crm_channel_events

Filtro: organizacao_id=eq.{'{orgId}'}

Evento: * (INSERT + UPDATE + DELETE)

Ação: invalida crm-leads-kanban, crm-leads-list, crm-radar, crm-radar-count

Canal 2 — crm-leads-inserts-realtime

Tabela: leads

Filtro: organizacao_id=eq.{'{orgId}'}

Evento: INSERT + DELETE

Ação: invalida os mesmos 4 query keys

Nota: UPDATE tratado separadamente em useCrmKanban

useCrmKanban — Canal Realtime UPDATE

Canal crm-leads-update-realtime escuta apenas UPDATE na tabela leads:

Se payload.new.awaiting_human === true e payload.old.awaiting_human !== true → exibe toast "Lead X aguardando atendimento humano" com duração 8s. Em seguida invalida crm-leads-kanban e crm-colunas-contagem.

handleDragEnd — Fluxo Completo

Validações antes de mover

RegraDestinos bloqueadosResultado

Triagem sem advogadotriagemtoast.error + rollback optimistic

Fluxo quando válido

1
Push no undoStack.current — max 10 itens, window de 5s (UNDO_TIMEOUT_MS)
2
Optimistic update: queryClient.setQueryData(['crm-leads-kanban', orgId], updater)
3
supabase.from('leads').update({ coluna_crm: novaColuna }).eq('id', leadId) — se erro: rollback
4
Fire-and-forget: INSERT em leads_atividades com tipo:'stage_change', descrição "Movido de X para Y" — invalida ['drawer-historico', leadId]
5
Fire-and-forget: busca whatsapp_conversas do lead → INSERT em mdzap_conversas_timeline com tipo:'crm_stage_change', metadata {'{coluna_anterior, coluna_nova, origem: "crm_kanban"}'}
6
Toast com action "Desfazer" (timeout 5s) — chama performUndo(leadId)
7
Após 2s: invalida ['crm-leads-kanban', orgId] e ['crm-colunas-contagem', orgId]

Undo Stack

Cada item: {'{leadId, leadNome, colunaAnterior, colunaNova, timestamp}'}. Expira em 5s. Ao desfazer: optimistic undo → supabase.update(colunaAnterior) → se erro: re-apply nova coluna.

Schema SQL — tabela restricoes

CREATE TABLE restricoes (
  id               UUID        DEFAULT gen_random_uuid() PRIMARY KEY,
  organizacao_id   UUID        NOT NULL REFERENCES organizacoes(id),
  lead_id          UUID        REFERENCES leads(id),
  cliente_id       UUID        REFERENCES clientes(id),
  empresa_id       UUID        REFERENCES empresas(id),
  empresa_nome     TEXT,
  orgao_nome       TEXT,
  tipo             TEXT        CHECK (tipo IN ('comprador','devedor','fiador','avalista')),
  codigo_contrato  TEXT,
  data_restricao   DATE,
  valor            INT8,       -- centavos
  processavel      BOOLEAN     DEFAULT TRUE,
  processo_id      UUID,       -- vinculado quando distribuído
  deleted_at       TIMESTAMPTZ, -- soft delete
  created_at       TIMESTAMPTZ DEFAULT now(),
  updated_at       TIMESTAMPTZ DEFAULT now()
);

Backend — SQL e Tabelas

VIEW view_crm_leads_kanban

CREATE VIEW view_crm_leads_kanban AS
SELECT
  l.id, l.organizacao_id, l.nome, l.cpf, l.data_nascimento,
  l.whatsapp, l.coluna_crm, l.atendente_id,
  u.nome  AS atendente_nome,
  l.advogado_id,
  adv.nome AS advogado_nome, adv.oab AS advogado_oab, adv.oab_uf AS advogado_oab_uf,
  l.origem_id, lo.nome AS origem_nome,
  l.estado_id, ed.uf   AS estado_sigla,
  l.awaiting_human, l.ultimo_contato, l.score, l.etiquetas,
  l.updated_at, l.created_at,
  -- Subquery tabela restricoes (fonte real, não JSONB)
  (SELECT COUNT(*) FROM restricoes r
   WHERE r.lead_id = l.id AND r.deleted_at IS NULL) AS restricoes_count,
  (SELECT COUNT(*) FROM restricoes r
   WHERE r.lead_id = l.id AND r.processavel = TRUE
   AND r.processo_id IS NULL AND r.deleted_at IS NULL) AS restricoes_processaveis_count,
  -- JSONB legado (campo documentos não tem tabela separada)
  (SELECT COUNT(*) FROM jsonb_array_elements(COALESCE(l.documentos,'[]'::jsonb)) d
   WHERE (d.value->>'situacao')='pendente') AS documentos_pendentes_count,
  l.indicacao_id,
  COALESCE(nota_agg.notas_count, 0) AS notas_count,
  nota_agg.ultima_nota
FROM leads l
LEFT JOIN users u               ON l.atendente_id = u.id
LEFT JOIN advogados adv         ON l.advogado_id = adv.id
LEFT JOIN leads_origens lo      ON l.origem_id = lo.id
LEFT JOIN estados_distribuicao ed ON l.estado_id = ed.id
LEFT JOIN LATERAL (
  SELECT COUNT(*) AS notas_count,
    (SELECT la2.descricao FROM leads_atividades la2
     WHERE la2.lead_id = l.id AND la2.tipo = 'nota'
     ORDER BY la2.created_at DESC LIMIT 1) AS ultima_nota
  FROM leads_atividades la
  WHERE la.lead_id = l.id AND la.tipo = 'nota'
) nota_agg ON true
WHERE l.deleted_at IS NULL

Gaps e Pendências

P0
1. Busca Kanban client-side (performance)
1000 leads carregados em memória, filtro com JS. Com mais de 500 leads pode ficar lento. Solução recomendada: paginação server-side por coluna com cursor (cursor-based pagination).
P0
2. leads.restricoes JSONB legado
Campo ainda existe na tabela mas NÃO é fonte de verdade. Fonte real = tabela restricoes. Nunca ler leads.restricoes diretamente — usar apenas a tabela relacional.
P1
3. leads.documentos JSONB sem tabela própria
Campo de documentos não tem tabela separada. documentos_pendentes_count na view usa este JSONB. Migração para tabela relacional pendente.
P1
4. awaiting_human sync unidirecional
MDZap → CRM funciona via Realtime. CRM → MDZap não tem sync automático. Webhooks WH-CRM-04/06/07/08 reservados mas não implementados.
P1

Service existe em crmWebhookService.ts mas webhook n8n não implementado — retorna noop.
P1
6. WH-CRM-05 WhatsApp individual
Service existe mas requer MDZap em produção para funcionar end-to-end.
P2
7. Pasta Drive pós-triagem
google_drive_folder_id criado manualmente ou via auditoria. Criação automática pós-triagem está pendente.
