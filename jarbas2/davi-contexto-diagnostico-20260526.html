Seção 1 — Como Funciona o Sistema de Distribuição

1.1 — O que é Auditoria
Consulta API Full (CP-Score)

Custo: aprox. R$ 2,99 por consulta

Retorna: todas empresas que negativaram o CPF na base 3 do SCPC/Boa Vista

Arquivo gerado: Relatório de Auditoria de Restrições de Crédito (PDF)

Esse PDF = "Comprovante BV" vai para o slot 6 do processo Boa Vista

Executada por: Júlia (IA) ao receber documento de identificação do lead

1.2 — O que é Boa Vista (duplo papel)
Boa Vista como Órgão Arquivista
  • Empresa que gerencia a base SCPC (Sistema Central de Proteção ao Crédito)
  • Arquiva restrições de TODAS as empresas credoras
  • Quando uma empresa negativar um CPF, registra na base BV
  • O relatório de auditoria mostra TODAS essas restrições consolidadas
Boa Vista como Empresa Ré
  • Se o cliente tem pendência financeira com a própria Boa Vista — processo contra Boa Vista
  • Usamos o mesmo relatório de auditoria como comprovante (já existe)
  • NÃO se gera novo comprovante para processo BV — usar o arquivo da auditoria
1.3 — Lógica de Restrições: Processáveis vs Não Processáveis
Tipo de Restrição Processável? O que acontece?
Pendência Financeira (empresa) SIM Vira processo individual + vai para processo BV
Restrição SCPC empresa SIM Vira processo individual + vai para processo BV
Restrição empresa NÃO processável NÃO (estratégico) NÃO vira processo, MAS vai para processo BV
Protesto em Cartório NÃO NÃO processa, NÃO vai para BV
Contumácia NÃO NÃO processa, NÃO vai para BV
Cheques sem Fundo NÃO NÃO processa, NÃO vai para BV
Nota: Empresas não processáveis são excluídas por decisão estratégica (risco alto de perda)
1.4 — Processo Boa Vista: como funciona
Etapa 1

MEF cadastra TODAS as restrições (processáveis + não processáveis) com: contrato, valor, data, nome empresa, tipo comprador

Etapa 2

Sistema calcula valor do processo BV = SOMA de todas restrições processáveis (EXCETO cartório/protesto)

Etapa 3 — Template

Verifica quantidade de restrições processáveis:

1 restrição — usa template "BV Única Restrição"

2+ restrições — usa template "BV Múltiplas Restrições"

Etapas 4 e 5

Processo BV trata: falta de notificação sobre CADA restrição

Comprovante = arquivo da auditoria (gerado pela Júlia) — não gerar novo

1.5 — Cada Restrição é Única

Triplo identificador: contrato + data + valor

  • A mesma empresa pode ter N restrições distintas (ex: 20 restrições da RGE — cada uma é um ato diferente)
  • Cada restrição processável = 1 processo separado
  • 1 processo BV por cliente (máximo)
1.6 — Pipeline Completa Lead para EPROC
Fase 1
Captação
Site/Criativo — Lead manda mensagem inicial (código + nome) via WhatsApp
Fase 2
Atendimento (Júlia IA + Humano)
Júlia pede doc identificação — faz auditoria SCPC R$2,99 — baixa PDF — manda ao lead
Humano: pede docs, cadastra CRM com MEF por empresa/variação, vincula restrições
ZapSign: procuração enviada — lead assina — Júlia recebe confirmação
Fase 3
Protocolo (Cátia)
Confere documentos nas pastas — junta PDFs multi-parte em 1 PDF — gera Situação Cadastral CPF (externo)
Confirma: contrato assinado salvo no CRM tier 1 (NÃO vai para pastas de processo)
Fase 4
Distribuição
CRM botão "Distribuir" (RPC) — lead vira cliente — entra em ag_preparacao
Fase 5
DAVI (ag_preparacao)
Trigger PostgreSQL detecta ag_preparacao — Edge Function davi-validar
Gera PI via webhook n8n — valida 6 slots — processa em paralelo (PI primeiro, 2-6 paralelo)
Erros — Revisão Humana (tab com drawer de documentos)
Aprovado — ag_distribuicao
Fase 6
MIA (ag_distribuicao)
Distribui processo no EPROC do estado correto

davi_validacoes

CREATE TABLE davi_validacoes ( id UUID DEFAULT gen_random_uuid() PRIMARY KEY, organizacao_id UUID NOT NULL REFERENCES organizacoes(id), processo_id UUID NOT NULL REFERENCES processos(id), slot_numero INT NOT NULL, -- 1 a 6 status TEXT CHECK (status IN ( 'pendente','aprovado', 'bloqueado','revisao_humana' )), erro_codigo TEXT, -- ex: 'residencia_conflito' -- 'procuracao_advogado_errado' erro_detalhe JSONB, -- dados extras: empresa emissora, -- campos divergentes, etc. validado_em TIMESTAMPTZ DEFAULT now(), force_revalidar BOOLEAN DEFAULT false, deleted_at TIMESTAMPTZ ); CREATE INDEX ON davi_validacoes(processo_id, slot_numero) WHERE deleted_at IS NULL;

davi_feedback_humano

CREATE TABLE davi_feedback_humano ( id UUID DEFAULT gen_random_uuid() PRIMARY KEY, organizacao_id UUID NOT NULL REFERENCES organizacoes(id), validacao_id UUID REFERENCES davi_validacoes(id), processo_id UUID NOT NULL REFERENCES processos(id), slot_numero INT NOT NULL, erro_codigo TEXT, descricao_humano TEXT, -- o que o humano observou resolucao TEXT, -- como foi resolvido estava_correto BOOLEAN, -- o erro do Davi era real? criado_em TIMESTAMPTZ DEFAULT now(), criado_por UUID REFERENCES auth.users(id) );

Seção 5 — Prompts de Diagnóstico: Rodar em Paralelo

Instrucao: Rode estes prompts no terminal em paralelo para verificar se os riscos são reais ANTES de implementar o Davi. Cada prompt é uma query SQL ou chamada de API independente. Supabase prod: qdivfairxhdihaqqypgb
RISK-03 % processos com nomenclatura correta
Supabase SQL Editor

Saber quantos processos em ag_preparacao já têm arquivos com nomenclatura no padrão N-

-- Verificar processos em ag_preparacao e arquivos no storage WITH processos_prep AS ( SELECT id, numero_cnj, cliente_id, advogado_id FROM processos WHERE status = 'ag_preparacao' AND deleted_at IS NULL LIMIT 100 ), total AS (SELECT COUNT(*) as total FROM processos_prep) SELECT total.total as processos_em_ag_preparacao, 'Verificar storage manualmente para nomenclatura' as proxima_acao FROM total;
RISK-05 UUID da Boa Vista no banco
Supabase SQL Editor

Encontrar o UUID real da empresa Boa Vista para configurar DAVI_BV_EMPRESA_ID

SELECT id, nome, categoria, processavel FROM empresas WHERE (LOWER(nome) LIKE '%boa vista%' OR LOWER(nome) LIKE '%scpc%' OR LOWER(nome) LIKE '%bv%') AND deleted_at IS NULL ORDER BY nome;
RISK-09 Ambiguidade no slot 5 (Renda vs Situação Cadastral)
Supabase SQL Editor

Ver quantos arquivos no storage têm nomes ambíguos no slot 5

-- Se existir tabela de documentos/anexos vinculada a processos SELECT nome_arquivo, COUNT(*) as qtd FROM documentos_processo -- ou o nome real da tabela WHERE LOWER(nome_arquivo) LIKE '5%' AND deleted_at IS NULL GROUP BY nome_arquivo ORDER BY qtd DESC LIMIT 50; -- Se a tabela nao existir, buscar no storage_objects: SELECT name, COUNT(*) as qtd FROM storage.objects WHERE bucket_id = 'processos' -- confirmar nome do bucket AND name LIKE '%/5%' GROUP BY name ORDER BY qtd DESC LIMIT 50;
RISK-10 IDs consistentes nos processos
Supabase SQL Editor

Confirmar que todos os processos têm organizacao_id, cliente_id, advogado_id preenchidos

SELECT COUNT(*) FILTER (WHERE organizacao_id IS NULL) as sem_organizacao, COUNT(*) FILTER (WHERE cliente_id IS NULL) as sem_cliente, COUNT(*) FILTER (WHERE advogado_id IS NULL) as sem_advogado, COUNT(*) FILTER (WHERE id_empresa IS NULL OR id_empresa = '') as sem_empresa, COUNT(*) as total FROM processos WHERE status IN ('ag_preparacao', 'ag_distribuicao') AND deleted_at IS NULL;

Supabase SQL Editor

Seção 6 — Script de Diagnóstico Pré-Implementação (Davi Dry Run)

Objetivo do Dry Run

Antes de implementar o Davi, rodar um script que analisa os processos existentes no CRM e calcula: % de processos que passariam com sucesso, quais slots têm mais problemas, quais erros seriam mais comuns e probabilidade de sucesso estimada por advogado.

O script vai
  1. Buscar todos processos em ag_preparacao (ou últimos 50 distribuídos)
  2. Para cada processo, verificar slots 1-6 no storage
  3. Verificar nomenclatura dos arquivos
  4. Calcular score de completude (0-6 slots presentes)
  5. Gerar relatório HTML com resultados
Quando rodar
  • P0 ANTES de implementar o Davi (diagnóstico)
  • Pos DEPOIS de implementar IMP-05 (verificar se nomenclatura melhorou)
  • Rec UMA VEZ POR SEMANA enquanto estiver em testes
