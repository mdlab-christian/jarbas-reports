O Agente Davi: Visao Completa

01 / 08

Davi e um sub-agente que prepara processos juridicos antes do ajuizamento via Mia no EPROC RS. Opera em dois modos distintos, cada um acionado em tabs diferentes da pagina /distribuicao.

Modo 1
Validar com Davi
Tab Ag. Preparacao Por processo

Valida um processo especifico antes de mover para "aguardando". Verifica peticao, comprovante, docs minimos, tipos obrigatorios, valor e storage.

Modo 2
Preparar Lote com Davi
Tab Ag. Distribuicao Ate 30 processos

Seleciona processos etapa_distribuicao = 'aguardando', filtra por OAB/TJRS/sem-CEF, abre ModalEnviarParaMia modo Davi com prontos/bloqueados/gerando.

Modo 1 — Fluxo de Validacao (7 verificacoes)
  1. Verifica peticao_status — se nao e 'sucesso' ou 'customizada' → dispara webhook PI (async, exclui do resultado imediato)
  2. Verifica comprovante por orgao — Boa Vista: apenas valida PRESENCA na pasta (Davi nao gera). Serasa/SPC/outros: se ausente → rpc_solicitar_comprovante_restricao + webhook (async)
  3. Conta docs na pasta de restricao (Tier 1 + Tier 2 juntos) ≥ 7
  4. TIPOS_OBRIGATORIOS cobertos: procuracao | identidade | residencia | renda_ctps
  5. restricoes.valor ≈ processos.valor_causa (tolerancia ± 10%)
  6. Storage HEAD check: docs acessiveis?
  7. Se APROVADO → UPDATE processos SET etapa_distribuicao = 'aguardando' + salva em davi_validacoes
Modo 2 — Fluxo de Montagem de Lote
  1. Seleciona ate 30 processos: OAB selecionada, apenas TJRS/RS, sem CEF (empresa_nome ILIKE '%caixa%' OR '%cef%'), check_distribuicao_rate_limit() sem duplicata no dia, ORDER BY prioridade DESC, dias_parado DESC
  2. Abre ModalEnviarParaMia (modo Davi) com 3 secoes: Prontos N ✓ Bloqueados N ✗ Gerando N ⏳
  3. Usuario seleciona OAB, modo (preview / ajuizamento direto), confirma
  4. Chama mia-preparar-lote com processos aprovados + davi_meta
O que o Davi GERA vs. so VALIDA
Orgao Reu Comprovante de Restricao Peticao Inicial
Boa Vista / SCPC ❌ Auditor upou — Davi so valida presenca ✅ Davi gera
Serasa / SPC / outros ✅ Davi gera via n8n ✅ Davi gera
Regra dos 7 docs: contagem POR PASTA DE RESTRICAO (por restricao_id), incluindo Tier 1 (gerais do lead) + Tier 2 (especificos da pasta). Se < 7 na pasta → bloqueia.
CEF: processos com reu CEF podem ir para Ag. Distribuicao normalmente, mas NAO sao selecionados para o lote da Mia.
Formato de issue salvo em davi_validacoes.issues[]
// Exemplo: tipo_ausente { "codigo": "tipo_ausente", "nivel": "bloqueante", "mensagem": "Falta Procuracao na pasta da restricao RGE SUL", "pasta_restricao_id": "uuid", "pasta_restricao_nome": "RGE SUL DISTRIBUIDORA DE ENERGIA S.A." } // Outros codigos possiveis: "peticao_gerando" → PI disparada async, aguardar "comprovante_ausente" → Comprovante nao encontrado na pasta "docs_insuficientes" → Contagem < 7 na pasta de restricao "valor_divergente" → Diferenca > 10% entre restricao.valor e processo.valor_causa "storage_inacessivel" → HEAD check falhou para doc_id "bv_comprovante_ausente" → Boa Vista: comprovante nao upado pelo auditor

Fluxo da Edge Function — por processo
  1. Valida JWT → get_org_id()
  2. Idempotencia via meta @> {batch_request_id}
  3. Busca cliente, lead, restricao mais recente

  7. Valida TIPOS_OBRIGATORIOS: procuracao | identidade | residencia | renda_ctps
  8. Minimo 5 docs em nomes_eproc (HARD BLOCK)
  9. INSERT em distribuicao_lotes com meta
  10. UPDATE etapa_distribuicao = 'em_distribuicao'
  11. INSERT em mia_eventos

Issues e Gaps Identificados

07 / 08
2 Bloqueantes P0 3 Avisos P1 2 Informativos P2 — Corrigir P0 antes de iniciar implementacao do Davi
G-01 P0 — Bloqueante ProcessoDrawerTabDocumentos hardcoda tipo_documento
Todo upload via ProcessoDrawer salva tipo_documento: 'comprovante_restricao' independente do que o usuario enviou. Um CNH upado por aqui vira comprovante_restricao no banco.

Impacto direto: badge de prontidao nao reconhece identidade/CNH upada por esse drawer. O Davi vai marcar o processo como "sem identidade" mesmo com o doc presente.

Fix: select de tipo_documento no dialog de upload do ProcessoDrawer + mapeamento correto antes do INSERT. Task T00 no checklist.
G-02 P0 — Bloqueante comprovante_restricao_status em processos, nao em restricoes
O status de comprovante esta em processos.comprovante_restricao_status, mas a restricao e a entidade-mae. Se o processo tiver multiplas restricoes, o campo e unico — ambiguidade critica.

Impacto no Davi: o Davi deve verificar por restricao_id em processos_documentos, nao apenas pelo campo de status do processo. O campo de status serve apenas como cache rapido, nao como verdade definitiva.

Regra de ouro: para validacao do Davi, sempre consultar processos_documentos WHERE restricao_id = $id AND tipo_documento = 'comprovante_restricao'.
G-03 P1 — Aviso google_drive_id armazena tanto Drive ID quanto storage_path
Em processos_documentos, google_drive_id e usado para Drive file ID e para storage_path de comprovantes gerados pelo n8n.

Antes de usar como Drive ID: verificar com isStoragePath(val) — se comecar com UUID de org ou "leads-docs/" e um storage_path, nao um Drive ID.

Prefira: drive_file_id_pdf e drive_file_id_docx que sao confiavelmene Drive IDs.
G-04 P1 — Aviso processos.google_drive_folder_id pode estar nulo
A PI gerada pelo n8n precisa da pasta Drive do processo. Se processos.google_drive_folder_id for nulo, o n8n falha silenciosamente ou salva sem Drive.

Davi deve verificar esse campo ANTES de disparar a geracao de PI. Se nulo → adicionar como issue bloqueante com codigo "drive_folder_ausente".

Sugestao de auditoria: SELECT COUNT(*) FROM processos WHERE google_drive_folder_id IS NULL AND etapa_distribuicao IN ('preparacao','aguardando')
G-05 P1 — Aviso useEnviarParaMia hook obsoleto ainda exportado
Faz INSERT direto em distribuicao_lotes sem chamar a Edge Function mia-preparar-lote. Risco de ser usado por acidente em novo componente.

Acao: remover antes de adicionar a logica do Davi para evitar confusao. Task T12 no checklist.
G-06 P2 — Info drive_pasta_id em restricoes DEPRECATED
Sunset agendado para 2026-05-17 (ja passou). Campo restricoes.drive_pasta_id deve ser migrado para google_drive_folder_id em restricoes antes do Davi usar este campo.

Nao bloqueia o MVP do Davi, mas pode causar falhas ao tentar sincronizar pasta de restricao com Drive.
G-07 P2 — Info Davi nao modifica o worker no MVP
davi_meta e gravado em distribuicao_lotes.meta, mas o worker distribuir-tjrs.mjs ignora essa chave. Para que o pre-trabalho do Davi (selecao de docs, nomes_eproc ja validados) beneficie o worker, o scheduler precisa ser modificado para injetar meta.davi_meta no ctx.

Identificado como D-17-A. Nao bloqueia o MVP, mas e necessario para aproveitar plenamente a pre-validacao do Davi na execucao EPROC.
