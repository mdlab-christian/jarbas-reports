O Grande Problema: ag_preparacao e Passiva Demais

Secao 03
🔴
Diagnostico P0
Hoje quando um processo entra em ag_preparacao, absolutamente nada acontece de forma automatica. O sistema e totalmente reativo — so age quando o usuario clica. Isso significa que erros so sao descobertos no momento da distribuicao, quando e tarde demais para corrigir rapidamente.
Consequencias do Estado Atual
  • 🔴Descoberta tardia: erros aparecem no momento da distribuicao
  • 🔴Nomes caóticos: "comprovante.pdf", "download (2).pdf" chegam sem slot
  • 🔴Carga cognitiva: usuario precisa identificar manualmente o que falta
  • 🔴PI manual: sem verificacao automatica se PI foi gerada
  • 🔴Valor errado: 44 de 76 processos com valor_causa incorreto — corrigivel automaticamente
  • 🔴Sem visibilidade: a lista de processos nao mostra nenhum badge de status Davi
Oportunidade de Automacao
  • ✅44 valores: 100% dos valor_divergente sao calculaveis automaticamente (15k + BV)
  • ✅Renomeacao: 90% dos docs sem slot tem nome identificavel (conteudo/padrao de nome)
  • ✅PI: verificacao e disparo de geracao e totalmente automatizavel
  • ✅Drive: criacao de pasta faltante e semi-automatica via webhook n8n
  • ✅Badge visual: realtime listener + davi_status em processos e suficiente
  • ✅Revalidacao auto: quando PI pronta, Davi revalida sem intervencao humana

Fase 2 em Detalhe — Identificacao e Renomeacao
🔍
Logica de Identificacao
Para cada documento sem slot number: analisa nome do arquivo (padrao de texto), extensao, e metadados do banco (tipo_documento, descricao). Nao requer leitura do conteudo para a maioria dos casos. Score de confianca calculado — docs com confianca abaixo de 70% ficam como "identificacao_manual_necessaria".
// Logica de identificacao por nome const tipoRules = [ { pattern: /rg|cpf|identidade|doc.*pessoal/i, slot: 1, nome: '1 - Identidade' }, { pattern: /procur/i, slot: 2, nome: '2 - Procuracao' }, { pattern: /resid|end|conta.*luz|conta.*agua/i, slot: 3, nome: '3 - Comprovante Residencia' }, { pattern: /renda|holerite|ctps|emprego/i, slot: 4, nome: '4 - Comprovante Renda' }, { pattern: /boa.*vista|scpc|serasa|restricao/i, slot: 5, nome: '5 - Comprovante Restricao BV' }, { pattern: /comprov.*pag|recibo/i, slot: 6, nome: '6 - Comprovante Pagamento' }, ]; // Por OAB: slot 6 tem nome diferente const slot6Names = { RS116571: '6 - COMPROVANTES', // Christian RS RS131163: '6 - Anexo', // Heloisa RS SC074025: '6 - COMPROVANTES', // Christian SC SC075466: '6 - Anexo', // Heloisa SC SP535101: '6 - COMPROVANTES', // Christian SP };

// Calculo correto para casos Boa Vista const restricaoValor = restricao.valor; // em centavos no banco const valorCorrecto = 1500000 + restricaoValor; // 15.000,00 + divida BV (centavos) // Tolerancia de 10% para variacao const tolerancia = valorCorrecto * 0.10; const atual = processo.valor_causa; // centavos const estaCorreto = Math.abs(atual - valorCorrecto) <= tolerancia; // Se incorreto: Davi auto-corrige (acao deterministica automatica) if (!estaCorreto) { await supabase .from('processos') .update({ valor_causa: valorCorrecto }) .eq('id', processo_id); // Registra em davi_validacoes como auto_corrigido }

Secao 05

Cada documento do processo tem um slot numerico fixo. O Davi usa esses slots para renomear e validar a presenca de cada tipo obrigatorio. O slot 6 varia por OAB do advogado responsavel.

1
Identidade
RG, CNH, CPF — documento pessoal principal
2
Procuracao
Variante por OAB: 2.0, 2.1, 2.2 — nao conta nos 7 obrigatorios
3
Comprovante Residencia
Conta luz, agua, telefone, declaracao municipal
4
Renda / CTPS
Holerite, extrato bancario, CTPS, declaracao IR
5
Comprovante Restricao
CRITICO — Boa Vista, SCPC, Serasa — obrigatorio para casos BV
6
Comprovante Pagamento
Nome varia: "COMPROVANTES" (RS116571, SP535101) ou "Anexo" (RS131163)
7+
Documentos Adicionais
Laudos, certidoes, declaracoes extras — sequenciais a partir do 7
—
Excluidos da Contagem
Procuracao, contrato, termo — nao entram nos 7 minimos

Acoes Deterministicas — Pipeline de Botoes

Secao 06
🎯
Principio de Design
Cada erro tem exatamente uma acao. Zero ambiguidade para o usuario. Zero botoes genericos como "Ver Mais" ou "Verificar". Cada botao e um verbo especifico com efeito imediato e rastreavel.
Codigo do Erro Label no UI Acao Executor
valor_divergente Corrigir Valor UPDATE processos.valor_causa = 15000 + restricao/100 + toast + Revalidar Davi auto
comprovante_bv_ausente Abrir Drive Abre pasta Drive do processo em nova aba para upload manual Usuario
docs_insuficientes Ver Documentos Navega para aba Documentos do processo (contexto: falta X docs) Usuario
tipo_ausente Ver Documentos Navega para aba Documentos + destaca o tipo especifico ausente Usuario
storage_ausente Fazer Upload Abre modal de upload para o documento especifico sem arquivo Usuario
drive_pasta_ausente Criar Pasta Chama webhook n8n para criar pasta Drive automaticamente Davi semi-auto
restricao_ausente Ver Restricoes Navega para aba Restricoes do processo Usuario
advogado_ausente Ver Processo Abre pagina completa do processo para vincular advogado Usuario
gerando_pi Aguardar Badge pulsante + notificacao MdZap quando PI pronta Davi watch
docs_sem_numero Renomear Docs Chama davi-renomear-docs EF — renomeia automaticamente com slot Davi auto
erro_validacao Revalidar force_revalidar = true — bypass cache 24h, reexecuta todos os checks Davi
Davi auto
Executa sem intervencao humana. Usuario ve resultado no badge.
Davi semi-auto
Davi dispara webhook mas aguarda confirmacao ou resultado externo.
Usuario
Requer acao fisica do usuario. Davi provee contexto maximo para facilitar.

O Que Precisa Ser Construido

Secao 08

Edge Functions

davi-ag-preparacao
Edge Function principal do sistema. Executa pipeline completo fases 1 a 6 de forma assincrona. Triggered por webhook n8n quando processo entra em ag_preparacao ou pelo botao "Reprocessar" do frontend.
P0 — Construir Assincrono Pipeline 6 fases
Inputs: processo_id, force_revalidar (bool)
Outputs: status, issues[], acoes[], davi_validacao_id
Side effects: UPDATE processos.davi_status, UPDATE processos.valor_causa (auto-correcao BV), INSERT davi_validacoes
davi-renomear-docs
Recebe processo_id. Lista docs sem slot number no banco e Drive. Identifica tipo por nome/conteudo com regras deterministicas. Renomeia no Drive e atualiza metadados no banco. Retorna relatorio detalhado de renomeacoes.
P0 — Construir Idempotente Drive API
Inputs: processo_id, dry_run (bool)
Outputs: renomeados[], ignorados[], erro_identificacao[]
Tolerancia: docs com confianca abaixo de 70% ficam em erro_identificacao
davi-status-badge
RPC leve para consulta rapida de status. Retorna davi_status, davi_issues_count e ultimo validado_em. Usado pelo frontend para badge em tempo real nos cards da lista de processos. Cache 5 minutos — nao consulta Drive ou Storage.
P1 — Semana Cache 5min Read-only
Inputs: processo_ids[] (batch suportado)
Outputs: {[processo_id]: {status, issues_count, validado_em}}
Performance: Single query com INDEX em davi_validacoes(processo_id, created_at DESC)
davi-validar (existente)
Edge Function ja existente. Continua funcionando para validacao manual de 1 processo. Sera refatorada para ser chamada internamente pelo davi-ag-preparacao como fase 3 e 4 do pipeline.
Existente Refatorar 7 checks
Mudanca necessaria: Exportar como funcao interna reutilizavel
Backward compatibility: Manter interface HTTP identica para chamadas existentes

-- Denormalizacao calculada ALTER TABLE processos ADD COLUMN davi_issues_count INT DEFAULT 0; -- Trigger para manter sincronizado CREATE OR REPLACE FUNCTION sync_davi_issues_count() RETURNS TRIGGER AS $$ BEGIN UPDATE processos SET davi_issues_count = ( SELECT jsonb_array_length(issues) FROM davi_validacoes WHERE processo_id = NEW.processo_id ORDER BY created_at DESC LIMIT 1 ) WHERE id = NEW.processo_id; RETURN NEW; END; $$ LANGUAGE plpgsql;

Automacao n8n

DAVI-AG-PREPARACAO-TRIGGER
Workflow responsavel por orquestrar o pipeline Davi quando um processo muda para ag_preparacao. Tambem faz o "watch loop" para PI e envia notificacoes MdZap.
  • Webhook trigger: chamado quando etapa_distribuicao muda para ag_preparacao (via DB trigger ou hook MdFlow)
  • Valida header mdflow: MdL1501@ — rejeita sem auth
  • Sticky notes: diagrama do fluxo completo documentado no workflow
  • Schema verify: confirma campos necessarios no payload (processo_id, org_id)
  • Registra em webhook_requests (LGPD 90d)
  • Chama davi-ag-preparacao EF com processo_id
  • Switch result.status → aprovado / bloqueado / gerando_pi
  • Se bloqueado: envia notificacao MdZap com issues resumidas e link para o processo
  • Se gerando_pi: inicia watch loop (poll mia_geracao_docs a cada 2 min por ate 30 min)
  • Quando PI pronta: chama davi-ag-preparacao novamente com force_revalidar=true
  • Response canonica: {success: true, action: "toast_refresh", message: "Davi finalizou analise"}
