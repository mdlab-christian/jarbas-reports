Secao 2 — Surpresas da Investigacao

⚡
Surpresa 1 — Valores Boa Vista ja estao no banco
restricoes.valor e um BIGINT em centavos — o valor da restricao ja foi cadastrado quando o auditor criou a restricao no sistema. Para comparar com o valor da PI (processos.valor_causa), o Davi nao precisa de LLM. Apenas WHERE restricoes.id = processo.restricao_id → comparar valores.
Zero custo LLM Dados ja no banco
⚡
Surpresa 2 — Anti-litigancia RPC ja existe
check_distribuicao_rate_limit(org_id, cliente_id, empresa_id) retorna {allowed: bool, reason: string} — a regra de nao repetir cliente × empresa no mesmo dia ja esta implementada no banco. O Davi usa, nao recria.
RPC pronta Zero codigo novo
⚡
Surpresa 3 — Ponto de injecao do Davi ja esta mapeado
O fluxo atual tem um botao "Enviar →" no card de preparacao que move o processo de etapa_distribuicao = 'preparacao' para 'aguardando'. O Davi entra exatamente aqui — valida ANTES desse botao funcionar. A estrutura visual ja existe.
Frontend existente Apenas adaptar
⚡
Surpresa 4 — davi_meta nao precisa de schema fixo
distribuicao_lotes.meta e JSONB livre. O Davi pode adicionar meta.davi_meta = {...} sem migration da tabela. O worker Mia ignora campos desconhecidos. Para que o worker USE os dados, apenas o scheduler precisa ser modificado para injetar ctx.davi_meta na execucao.
JSONB flexivel Migration opcional

Secao 4 — 9 Novas Decisoes (D-09 a D-17)

D-09
Validacao de valores Boa Vista: banco vs PDF?
A investigacao revelou que restricoes.valor (centavos BIGINT) ja esta no banco. A questao e: o comprovante PDF pode ter um valor diferente do que foi cadastrado.
A
Comparar restricoes.valor vs processos.valor_causa (ambos no banco — sem LLM, instantaneo) Recomendado
B
Extrair valor do PDF via LLM e comparar com processos.valor_causa (mais preciso, mas custo)
C
Apenas verificar presenca do comprovante + restricoes.valor > 0 (sem comparar valores)
Por que A? O valor foi cadastrado pelo auditor ao criar a restricao — e a fonte primaria. Se divergir do PDF, e um problema de cadastro, nao de documento.

D-10
Como identificar processos CEF para excluir?
A investigacao nao encontrou campo especifico. A empresa reu esta na tabela empresas com empresa_nome. CEF = "Caixa Economica Federal".
A
restricoes.empresa_nome ILIKE '%caixa%' OR ILIKE '%cef%' — flexivel, sem manter lista Recomendado
B
Campo empresas.categoria = 'cef' — mais preciso, mas precisa verificar se campo existe
C
Config na tabela distribuicao_configuracoes — campo excluir_empresas_nomes TEXT[] (configuravel pelo admin)

Davi valida processo a processo ou em batch ao clicar no botao?
Quando e como acontece a validacao dos processos elegíveis para o lote.

D-15
Onde vive a logica de validacao do Davi?
Com os dados da investigacao, temos opcoes mais concretas sobre onde orquestrar as queries de validacao.
A
Nova Edge Function davi-preparar-lote — orquestra validacoes, le banco, salva em davi_validacoes, retorna issues Recomendado
B
Logica no frontend (React hooks) — queries diretas ao Supabase sem EF, sem servidor intermediario
C
N8n workflow que orquestra as queries e validacoes via webhook
Por que A? Edge Function tem acesso direto ao banco, sem CORS, com timeout de 60s suficiente para 30 processos × validacoes rapidas (apenas banco, sem PDF parsing).

D-16
Schema de davi_validacoes: minimo ou completo?
Com base nos findings, o schema pode ser mais enxuto ou ter campos explícitos por validacao.
A
Schema minimo: id, organizacao_id, processo_id, resultado, issues JSONB, davi_meta JSONB, deleted_at Recomendado
B
Schema rico com campos explicitos: peticao_ok BOOL, comprovante_ok BOOL, docs_count INT, tipos_cobertos TEXT[], divergencia_valor_pct NUMERIC, etc.
C
Sem tabela — salvar tudo em processos_documentos como doc de auditoria ou em processos.meta JSONB
Por que A? O JSONB e flexivel — Davi pode evoluir o schema sem migrations. Campos explicitos sao bons para queries agregadas, mas para fase 1 o JSONB basta.

D-17
O worker Mia precisa ser modificado para consumir davi_meta?
A investigacao mostrou que o worker re-queries tudo e so usa nomes_eproc do meta. Para que o Davi seja util, o worker precisaria consumir davi_meta.
A
Fase 1 sem mudanca no worker — Davi valida e prepara, worker faz como hoje. davi_meta fica como auditoria. Recomendado MVP
B
Modificar scheduler para injetar meta.davi_meta.cliente_cidade e outros dados no ctx do worker
C
Modificar worker para usar ctx.davi_meta.nomes_eproc ao inves de ctx.nomes_eproc (fonte secundaria)
Por que A? Menor risco no MVP. O worker validado funciona. O valor do Davi e na preparacao e selecao dos processos, nao na execucao EPROC.
