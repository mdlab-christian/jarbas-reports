Perguntas de Decisao de Arquitetura

Q-01 Validacao da Peticao Inicial: como comparar template vs categoria?
A PI e gerada por webhook n8n usando um template especifico por categoria de empresa. A categoria esta em empresas.categoria vinculada ao id_empresa do processo. Davi precisa confirmar que a PI gerada usou o template correto.
A Davi consulta a PI gerada + consulta empresas.categoria + tem tabela de mapeamento categoria → template_id e compara
B A PI ja vem com metadado do template usado (n8n inclui no arquivo ou em tabela), Davi so compara metadado com a categoria da empresa
C n8n ja valida categoria ao gerar e retorna erro se errado; Davi so verifica se PI existe e esta na OAB correta
⭐ Recomendacao: Opcao B — metadado de template no arquivo/tabela e mais confiavel que re-analise, menos chance de drift

Q-02 Procuracao: como extrair os campos dos placeholders com GPT?
Procuracao e gerada via ZapSign com placeholders (nome_cliente, cpf_cliente, nome_advogado, oab_advogado, etc.). GPT-4.1 Mini vai ler o PDF. Para nao desperdicar tokens analisando o documento inteiro, Davi deve mirar nos campos certos.
A Passar o PDF completo ao GPT com prompt "extraia apenas estes campos: [lista de campos]" — GPT retorna JSON com os campos
B Ter um template de prompt por advogado (Christian/Heloisa) mapeando a posicao visual dos campos no PDF e instruindo o GPT onde olhar
A+B Opcao A para extracao geral, Opcao B como fallback de localizacao se confianca for baixa
C Extrair texto via PDF parser (pdfjs/poppler) antes de enviar ao GPT, reduzindo o que ele precisa processar
⭐ Recomendacao: Opcao A + B combinados — A para extracao geral, B como fallback se confianca baixa

Q-03 Identidade vs CNH: quao confiavel e a distincao do GPT?
GPT-4.1 Mini distingue CNH de RG pelo layout visual. CNH tem "CARTEIRA NACIONAL DE HABILITACAO", campo de categoria (A/B/C), renach, data 1a hab. RG/Identidade tem "CARTEIRA DE IDENTIDADE", numero RG, orgao expedidor (SSP, PC, etc.). Playbook treinado com 17 documentos (10 RG, 7 CNH).
A Confiar 100% no GPT para classificar, registrar o tipo identificado e passar para a Mia
B GPT classifica + retorna score de confianca; se confianca < 80% — mover para Revisao Humana com badge "Identificar tipo manualmente"
C Usar OCR para buscar string exata "CARTEIRA NACIONAL" ou "CARTEIRA DE IDENTIDADE" no texto extraido, sem GPT para esse slot especifico
⭐ Recomendacao: Opcao B — score de confianca e essencial para nao errar tipo no EPROC

Q-04 Slot 4 (Residencia) com conflito: o que acontece depois da badge?
Davi detecta que o comprovante de residencia e da mesma empresa re. Coloca badge com nome da empresa. Processo vai para Revisao Humana. Mas o que acontece com o slot 4 — o arquivo e mantido ou removido?
A Manter arquivo na pasta + badge de alerta + processo vai para Revisao Humana. Humano decide o que fazer.
B Soft-delete do arquivo conflitante + badge + Revisao Humana (Davi decide que o arquivo e invalido)
C Mover arquivo para subpasta _revisao/ dentro da pasta do processo + badge + Revisao Humana

Q-05 ID_empresa da Boa Vista: onde configurar?
Davi nao deve gerar processo para o id_empresa da Boa Vista no banco. Precisa saber qual e esse ID e onde ele fica armazenado para consulta em tempo de execucao.
A Variavel de ambiente DAVI_BV_EMPRESA_ID=<uuid> na Edge Function (configurar uma vez, flexivel)
B Tabela Supabase davi_config com chave='bv_empresa_id' e valor=<uuid> — Davi consulta ao iniciar
C Hardcode do UUID diretamente no codigo (mais simples mas fragil se mudar)
⭐ Recomendacao: Opcao A — variavel de ambiente e o padrao para configuracoes sensiveis de Edge Functions

Q-06 Tabela de validacoes do Davi: criar nova ou usar existente?
Davi precisa persistir o resultado de cada validacao por slot (aprovado/bloqueado/pendente) para o frontend exibir e para evitar reprocessamento desnecessario.
A Criar tabela davi_validacoes com campos: id, processo_id, slot_numero, status, erro_codigo, erro_detalhe, validado_em, force_revalidar
B Usar campo JSONB validacao_davi na tabela processos ja existente (sem nova tabela)
C Usar a tabela processos_davi_validacoes se ja existir (verificar antes de criar)
⭐ Recomendacao: Opcao A — tabela separada permite historico, indices eficientes, soft-delete por slot sem afetar tabela core

Q-07 Gatilho para o Davi iniciar: como sabe que um processo entrou em ag_preparacao?
Quando o lead e distribuido via botao no CRM, ele entra em ag_preparacao. O Davi precisa comecar a trabalhar nesse momento — a latencia de inicio impacta diretamente o tempo total do fluxo.
A Trigger PostgreSQL no UPDATE de status = 'ag_preparacao' → chama Edge Function davi-iniciar via pg_net
B n8n monitora a tabela de processos com polling a cada X minutos e dispara quando detecta status = ag_preparacao
C Frontend dispara webhook para o Davi ao mudar o status para ag_preparacao (no mesmo momento do RPC de distribuicao)
⭐ Recomendacao: Opcao A — trigger PostgreSQL e o mais confiavel e imediato, sem depender de frontend ou polling

Q-08 Sequencia de processamento dos 6 slots: paralelo ou sequencial?
Os 6 slots tem dependencias diferentes. A PI (slot 1) precisa ser gerada primeiro via webhook antes dos outros slots. Os slots 2-6 podem ser validados de forma independente.
A Sequencial 1 → 2 → 3 → 4 → 5 → 6 (mais simples, mais lento)
B Gerar PI (slot 1) primeiro → depois validar slots 2-6 em paralelo (mais rapido)
C Todos em paralelo, incluindo slot 1 (mais rapido mas requer tratamento de estado mais complexo)
⭐ Recomendacao: Opcao B — PI precisa de webhook assincrono, faz sentido separar. Demais podem ser paralelos.

Q-09 Quando multiplas restricoes processaveis da mesma empresa: 1 ou N comprovantes BV?
Se o cliente tem 3 restricoes processaveis contra a mesma empresa (ex: 3 dividas com Porthal Escola), cada uma vira um processo separado. Cada pasta de processo no EPROC precisa do comprovante BV. Mesmo arquivo ou copias fisicas?
A Um comprovante BV por pasta de processo (arquivo copiado/linkado em cada pasta)
B Um comprovante BV referenciado por todos os processos via link/URL (economiza storage)
C Davi verifica se o slot 6 ja tem comprovante, se nao tiver copia do processo irmao automaticamente
⭐ Recomendacao: Opcao A — EPROC exige arquivo fisico em cada processo, nao links. Copia e mais segura.

B Coluna adicional no kanban de distribuicao (ao lado das existentes)
C Badge/contador no header da pagina que abre drawer lateral com os processos em erro

Q-13 Nomenclatura automatica dos arquivos ao entrar em ag_preparacao (IMP-05): quando implementar?
IMP-05 = renomear arquivos do storage para formato 1-, 2-, etc. ao entrar em ag_preparacao. Sem isso, Davi precisa "adivinhar" qual arquivo e qual slot pelo conteudo — aumentando muito a margem de erro.
A Implementar IMP-05 ANTES do Davi (pre-requisito)
B Implementar IMP-05 em paralelo com o Davi, mas nao bloquear o inicio do desenvolvimento
C Davi funciona sem IMP-05 (identifica por GPT + conteudo), IMP-05 fica como melhoria futura
⭐ Recomendacao: Opcao A — sem nomenclatura padronizada, o Davi precisa "adivinhar" qual arquivo e qual, aumentando muito a chance de erro

Q-14 Estrategia de rollout: implementar Davi por slot ou tudo junto?
Sao 6 slots com logicas diferentes. Pode implementar tudo de uma vez ou slot a slot. A escolha impacta velocidade de entrega de valor vs risco de regredir o fluxo atual.
A Implementar todos os 6 slots de uma vez (mais risco, mais rapido para ter resultado completo)
B Slots 1 a 6 progressivamente: 1 semana por slot, testes com clientes reais a cada slot adicionado
C Implementar Slot 1 (PI) + Slot 2 (Procuracao) + Slot 6 (Comp. Restricao) primeiro como MVP, depois slots 3-4-5
⭐ Recomendacao: Opcao C — PI, Procuracao e Comp. Restricao sao os mais criticos e mais impactantes. MVP funcional mais rapido.
