Seção 3 — 7 Decisões Finais (Rodada 3)

D-18
O Davi busca de ‘preparacao’ OU ‘aguardando’ OU ambas as etapas?
O fluxo atual tem processos em dois estados relevantes. O botão fica em “Ag. Distribuição” mas os processos a validar podem estar em “Ag. Preparação”.
A Busca de AMBAS — valida os de ‘preparacao’, move aprovados para ‘aguardando’, seleciona lote dos ‘aguardando’ (novo + existentes) Recomendado
B Apenas de ‘aguardando’ — Stage A (preparação→aguardando) fica com o fluxo manual existente
C Apenas de ‘preparacao’ — o lote sai diretamente da preparação para a Mia sem passar por ‘aguardando’
Por que A? O usuário disse “o davi vai passar todos que estiverem corretos para ag distribuicao” — implica que o Davi age sobre processos em preparação também. A opção A maximiza o valor do Davi em um único clique.

Davi gera comprovante de restrição automaticamente se ausente?
Existe webhook /webhook/mdflow/doc/gerar-comprovante e RPC rpc_solicitar_comprovante_restricao. O usuário disse “gerar os comprovantes” no contexto do Davi.
A Sim — dispara geração automaticamente (async / fire-and-forget), exclui do lote atual, avisa “gerando comprovante” no modal Recomendado
B Não — apenas bloqueia e sinaliza para o usuário gerar manualmente
C Bloqueia mas abre sub-modal perguntando “Deseja gerar agora?” antes de prosseguir

D-20
Geração de PI: aguarda resposta do webhook ou dispara e exclui do lote?
O webhook n8n de PI pode demorar 10–30s. A Edge Function tem timeout de 60s — com 30 processos aguardando resposta simultânea, o risco de estourar é real.
A Fire-and-forget — dispara webhook e exclui do lote atual com status “gerando PI”. No próximo clique estará pronto se o webhook concluir Recomendado
B Aguarda webhook até 30s; se concluir, inclui no lote; se timeout, exclui com aviso
C Não gera PI — apenas verifica se existe. Geração é responsabilidade do usuário antes de chamar o Davi

D-21
A regra dos 7 docs se aplica por pasta (por restrição) ou por processo?
O usuário disse “mais de 7 docs nas pastas por restricoes”. Um processo pode ter múltiplas restrições. A mia-preparar-lote atual valida por processo (total ≥ 5 em nomes_eproc depois da limpeza).
A Por processo — soma todos os docs do processo (lead docs + processo docs) ≥ 7. Alinha com a lógica atual da mia-preparar-lote Recomendado
B Por pasta de restrição — cada pasta (restricao_id) precisa ter ≥ 7 docs individualmente. Mais rigoroso, pode bloquear muitos processos
C Por processo mas separado: ≥ 4 docs Tier 1 (gerais) + ≥ 3 docs Tier 2 (pasta da restrição específica)
Nota: espelhar a lógica da mia-preparar-lote reduz risco de aprovação pelo Davi seguida de rejeição pela Mia (R-Residual-3).

D-22
Badge no card de Ag. Preparação: real-time ou apenas pós-Davi?
A investigação mostrou que o badge de prontidão (TIPOS_OBRIGATORIOS) já existe no drawer do cliente. Na tab de preparação do processo, não há badge ainda. Os dados necessários já estão no banco.

O que o modal modificado (ModalEnviarParaMia modo Davi) mostra antes de enviar?
A Três seções distintas: “N prontos [v]” (lista expansível) + “N bloqueados [x]” (colapsada com motivos por processo) + “N gerando [...]” (async). Botão confirmar envia apenas os aprovados Recomendado

D-24
Quando processos com docs faltando voltam para ‘preparacao’ após bloqueio pelo Davi?
Processos bloqueados pelo Davi podem já estar em ‘aguardando’ (foram movidos anteriormente) ou permanecer em ‘preparacao’. A questão é sobre reversão de estado.
A NãO reverter estados — processos em ‘aguardando’ que falharam ficam em ‘aguardando’ com badge de bloqueio. O usuário decide explicitamente se devolve para preparação Recomendado
B Reverter para ‘preparacao’ automaticamente quando Davi detecta problema grave (sem PI, menos de 7 docs)
C Perguntar ao usuário para cada bloqueado: “Devolver para preparação?” — controle total mas mais interação
Por que A? Reversão automática de estado pode surpreender o usuário e desfazer trabalho manual anterior. Manter o estado e sinalizar o problema é mais seguro e reversível.

Seção 5 — Riscos residuais (pós-decisão)

R-Residual-1
Timeout EF com 30 processos + HEAD checks
Contexto: 30 processos × HEAD check no storage = potencial de timeout na Edge Function (limite 60s).

Mitigação: Paralelizar todos os HEAD checks via Promise.allSettled. Se resultado for rejected, marcar como ‘arquivo_inacessivel’ sem falhar o lote inteiro.
R-Residual-2
Race condition entre Davi e clique manual “Enviar”
Contexto: Se o usuário clicar “Enviar para Mia” manualmente enquanto Davi está validando o mesmo processo, pode haver UPDATE duplo em etapa_distribuicao.

Mitigação: Idempotência — UPDATE somente se etapa_atual = valor esperado. Ex: WHERE etapa = 'preparacao' antes de mover para ‘aguardando’.
R-Residual-3
Davi aprova mas mia-preparar-lote rejeita
Contexto: Redundância de validações pode produzir rejeição inesperada pelo worker da Mia após aprovação pelo Davi. Gera confusão para o usuário.

Mitigação: Logar divergência no campo davi_meta dentro do lote e mostrar motivo detalhado na UI do modal de resultado.
