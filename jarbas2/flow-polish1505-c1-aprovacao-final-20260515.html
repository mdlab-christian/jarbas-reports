Solução definitiva blocos — como funciona agora

Como funciona o estágio G5e

O fluxo VibeLaw agora tem um estágio G5e novo que injeta blocos como fundamentação obrigatória antes do Sonnet gerar.

Fluxo G5e — passo a passo
1. Pipeline detecta categoria empresa (IF cartão / BV / outra)
2. Selector IF/BV escolhe modelo certo (Christian v1 / Heloísa v3)
3. G5e busca top 10 blocos texto filtrados:
  • categoria_id = match peça
  • version = match advogado (v1 Christian / v3 Heloísa)
  • ordem por relevância/uso histórico
4. Injeta tag XML <blocos_fundamentacao_disponiveis> no prompt:
<bloco_1>{conteudo R-BFD-01}</bloco_1> <bloco_2>{conteudo R-BFD-02}</bloco_2> ... <bloco_10>{conteudo R-BFD-05}</bloco_10>
5. Instrução explícita no prompt:
"Você DEVE usar os blocos acima como fundamentação obrigatória nas seções correspondentes. Adapte dados (cliente, valor, contrato) mas preserve a argumentação técnica original."
6. Sonnet gera peça INCORPORANDO blocos como base
7. Log telemetria: G5e: blocos_fundamentacao injetados=10
ANTES

Sonnet inventava argumentação genérica (peças "boas" mas órfãs do escritório).

DEPOIS

Sonnet recebe blocos do escritório como CONTEXTO OBRIGATÓRIO → peça incorpora fundamentação real da equipe.

Por que isso não foi resolvido em c1?

O foco em c1 foi: validação de prompts + ordem canônica + Boris validators. Ninguém investigou se os blocos estavam efetivamente chegando ao Sonnet via prompt. A causa raiz era invisível porque:

  • Logs não mostravam (G5e não existia)
  • Modelos IF Christian existem mas são 280-340K chars (auto-suficiência rejeita)
  • tag_answers={} deixava Caminho A nunca disparar (Caminho B só consultava modelo)
  • Pipeline assumia "blocos vêm pela tag, peça sem tags não usa blocos" — premissa silenciosamente errada
