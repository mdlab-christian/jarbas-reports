Questao Aberta — Roteamento OAB → agent_slug

🎯 Esta e a unica decisao tecnica pendente do planning. O contexto: Tania = atendimento_cp → OABs de Christian (RS116571, SC074025, SP535101) | Raquel = atendimento_hm → OABs de Heloisa (RS131163, SC075466). O trigger parte do advogado_id no processo.
Opcao A — Hardcode no n8n Recomendada para MVP
No workflow n8n do trigger, um Set/Switch node com os 5 OABs mapeados para os 2 slugs.
PROS
  • Zero banco, zero migracao
  • Visivel no workflow
  • Facil de debugar
CONS
  • Novo advogado = editar workflow
Quando usar: MVP, equipe pequena e estavel
Opcao B — Campo agente_slug na tabela advogados/usuarios
Adicionar coluna agente_slug TEXT CHECK (...). n8n busca via RPC: SELECT agente_slug FROM usuarios WHERE id = p_advogado_id.
PROS
  • Dinamico e escalavel
  • Editavel na UI
CONS
  • Requer migration
  • Campo novo, nem todos tem agente
Quando usar: quando houver terceiro advogado na equipe
Opcao C — Lookup via jarbas_accounts
Tabela ja tem os OABs com credenciais EPROC. n8n faz lookup: OAB do advogado → jarbas_accounts → mapeia slug por logica de negocio.
PROS
  • Reutiliza dados existentes
CONS
  • Acoplamento com tabela JARBAS
  • Logica nao obvia
Quando usar: nao recomendado — risco de acoplamento desnecessario
✅ Recomendacao: Opcao A para o MVP. Quando houver terceiro advogado, migrar para Opcao B. Custo de migracao e baixo (1 campo + 1 query n8n).
