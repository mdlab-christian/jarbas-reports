🔌 O segredo: Realtime como cola

O Mac Mini roda o pipeline (pode levar 60-120s). O frontend não fica em loop de polling — usa Supabase Realtime via PostgreSQL changes em olivia_historico. Quando o Mac Mini escreve etapa_atual = 'S3' ou status = 'CONCLUIDO', o frontend recebe em milissegundos. Zero polling. Zero race condition. Limpo.

🎯 Decisões que Você Precisa Tomar

Clique na opção que você escolhe. 8 decisões, algumas críticas — sem elas o projeto fica travado.

D-01
Onde roda o gerador de petições — Mac Mini ou Edge Function pura?
Hoje o Mac Mini executa o pipeline S0→S9. Há uma alternativa de migrar tudo para Edge Functions (Deno) sem depender de hardware local.
CRÍTICA
D-02
Quantas abas simultâneas de petição o wizard suporta?
Spec atual diz máximo 5. Mas cada aba em geração consome recursos do Mac Mini. E a UX de múltiplas abas tem overhead de Zustand + state management.
IMPORTANTE
D-03
VibeLaw — editor simples ou split view completo com minimap?
TipTap completo (split view + minimap + Cmd+K + diff) é a spec D13. Mas é complexo de implementar corretamente e pode atrasar o prazo. Alternativa: editor funcional primeiro, polish depois.
IMPORTANTE
D-04
Como tratar timeout/erro durante geração (Mac Mini fora do ar)?
Hoje quando o Mac Mini cai, o usuário fica preso na tela de loading infinito. Precisa de uma estratégia de fallback clara.
CRÍTICA
D-05
Upload de documentos no Step 1 — OCR é P0 ou P2?
A spec prevê OCR de PDFs escaneados via Sonnet 4.6 Vision. Mas 80% das petições não precisam de documentos extras — processo já tem peças no EPROC. OCR atrasa o time-to-first-petition.
MODERADA
D-06
Qual modelo IA para os VibeLaw slash commands?
D13 especifica Sonnet 4.6 para VibeLaw. Mas /reescrever de um parágrafo é simples — Haiku 4.5 seria 10x mais barato e 3x mais rápido para edições rápidas.
MODERADA
D-07
Onde fica o Step de análise de provas — integrado ou separado?
A spec v3 original tinha uma "AnaliseCompacta" no Step 2 mostrando score 0-10 + pilares + alertas. Útil para o advogado entender a força da tese antes de gerar.
MODERADA
D-08
Por onde começar — Frontend ou Mecanismo (Mac Mini)?
Dois caminhos possíveis para retomar o projeto. Backend (migrations) já está quase pronto. O gargalo é Mac Mini ERROs ou Frontend incompleto?

🔴
Risco #1 — Mac Mini como ponto único de falha
Se o Mac Mini cair (energia, rede, update), o OlivIA para completamente. Hoje não tem retry, healthcheck ou fila.
Mitigação: useMacMiniHealth (healthcheck 30s) + fn_olivia_retry + timeout 120s com toast de aviso.
🟡
Risco #2 — TipTap + VibeLaw = débito técnico potencial
SlashMenu, DiffHighlighter, e SectionNav integrados ao TipTap são difíceis de testar. Bug em um quebra os outros.
Mitigação: Implementar VibeLawExtension de forma isolada, com testes unitários separados do editor.
🟡
Risco #3 — Zustand com múltiplas abas em geração
Cada aba tem seu Realtime subscription. 5 abas simultâneas = 5 channels abertos. Estado pode dessincronizar.
Mitigação: Limitar para 3 abas (D-02 opção A) e centralizar subscriptions no hook useOliviaStatusRealtime.
🟢
Ponto forte — Backend já está 70% pronto
Waves 1 e 2 concluídas. Tabelas migradas, fn_rag_search_v3 corrigida, embedding_google funcionando. O frontend tem base sólida.
Ação: Priorizar diagnóstico do Mac Mini (D-08 opção B) para desbloquear a integração ponta-a-ponta.

→
Domínio específico: negativação indevida + EPROC (TJRS/TJSC/TJSP). Os 16 playbooks cobrem exatamente os réus do Midas. RAG em 1.353 jurisprudências relevantes.
→
Volume alto: 5.800 processos = usar OlivIA todo dia. Cada 1% de melhoria na taxa de sucesso = 58 petições a mais por ciclo.
→
Equipe pequena: Não precisa de multi-tenant de verdade. Midas-only simplifica RLS, VibeLaw prompts e onboarding.
🎯 O projeto perfeito para esse contexto
1.

Mac Mini estável > Edge Functions bonitas: O que importa é gerar petição. Hardware local com pipeline bem debugado > arquitetura elegante instável.
