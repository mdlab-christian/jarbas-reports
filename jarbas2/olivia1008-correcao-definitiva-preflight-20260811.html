Correção definitiva do preflight no ChatGPT

Redesenho do contrato de aprovação para eliminar a hash da conversa, impedir que o HTML bloqueie o fluxo e manter a conferência humana antes de qualquer petição.

Recomendação: aprovar HTML continua principal Hash somente interna 2 ferramentas públicas Zero perda de auditoria
Veredito Trocar o gate, não abandonar o preflight.

O desenho atual tornou uma camada visual opcional em requisito obrigatório de negócio. A solução é usar o ID imutável como contrato público e deixar hash, versão e idempotência inteiramente no backend.

1

Diagnóstico honesto

Por que as correções anteriores não resolveram definitivamente.

Erro de arquitetura assumido: transformamos a renderização do MCP App em gate obrigatório. A orientação oficial da OpenAI é que a UI seja opcional e que as ferramentas continuem úteis quando o cliente não renderiza o componente. O nosso fluxo atual faz o oposto.
Causa 1

HTML virou regra de negócio

aprovacao_aprovar consulta report_url e bloqueia com PREFLIGHT_HTML_AUSENTE. Isso mistura “o relatório foi gerado” com “o usuário realmente viu o painel”. Uma coisa não prova a outra.

Causa 2

Hash vazou para o modelo

O GPT precisa receber, conservar e repetir selection_hash em aprovação e geração. A hash é útil para o backend, mas é um detalhe técnico frágil e desnecessário na conversa.

Causa 3

Tool choreography excessiva

Hoje o agente coordena criar → validar âncoras → exibir → aprovar → gerar, além de versões e dupla geração. Cada chamada adicional aumenta a chance de pular, repetir ou perder contexto.

Causa 4

KB tornou a falha definitiva

A KB ordena “sem fallback”, “exatamente uma vez” e “pare se o painel não abrir”. Assim, uma limitação de UI interrompe um caso juridicamente pronto.

Causa 5

Fontes repetidas

A mesma regra aparece nas instructions, KB, três skills e instructions do MCP. Patches sucessivos criam drift e tornam o comportamento difícil de prever.

Conclusão

A hash não é a causa isolada

Apagá-la do banco não faria o iframe renderizar. A correção definitiva é remover a hash da interface pública, tornar a UI não bloqueante e reduzir o fluxo para duas operações de alto nível.

3

Nova arquitetura: Preflight v2

HTML principal quando suportado; fluxo funcional mesmo sem iframe.

1 · GPT analisaProcesso, provas, modelo, tags, blocos e complementos.
2 · preflight_prepararUma chamada cria a versão, valida regras/âncoras e devolve o snapshot visual.
3 · ConferênciaMCP App HTML abre inline. Se o host falhar, surge resumo estruturado equivalente.
4 · Ordem humanaUsuário responde “aprovar” ou informa ajustes. Ajuste cria nova versão.
5 · preflight_confirmarUma chamada atômica aprova e executa a ação adequada ao modo.
Tool 1

preflight_preparar

Entrada: modo, processo, seleção e pendências. Sem hash.

Backend: cria vN imutável, calcula fingerprint interna, valida bloqueios e — no VibeLaw — resolve âncoras.

Saída: preflight_id, versão, prontidão e structuredContent. A própria tool possui o template do MCP App; não existe chamada posterior para “exibir”.

Tool 2

preflight_confirmar

Entrada: somente preflight_id e a ação humana (aprovar ou ajustar). Sem hash.

Backend: verifica se é a versão vigente, se não há bloqueios, registra o usuário e usa o snapshot salvo.

Saída: wizard no /peticao, geração única no /sb ou job FIEL+VIBELAW no /vibelaw.

Sobre “o GPT gerar o HTML direto”: o GPT pode produzir texto com tags HTML ou um arquivo, mas isso não equivale a uma interface HTML segura dentro da conversa. O método oficial para UI inline é o MCP App em iframe. Portanto, o HTML continuará vindo do MCP; o GPT fornece os dados e conduz a decisão. A diferença é que a renderização deixa de controlar a regra de negócio.

Máquina de estados simplificada

preparando→aguardando_aprovacao→aprovado→em_execucao→concluidofalhou

Nova versão invalida a anterior. O banco impede aprovar versão antiga por grupo_id + maior versao; não depende de uma hash enviada pelo cliente.

4

Comportamento nos três modos

Mesmo contrato de conferência; ação final diferente por modo.

/peticao

Preflight → wizard

  1. GPT analisa e recomenda estratégia.
  2. preflight_preparar mostra a seleção.
  3. Usuário aprova.
  4. preflight_confirmar cria a sessão e devolve o deep link do MdFlow.
  5. A seleção final dos blocos continua no frontend.

Não gera petição no GPT e não precisa de hash pública.

/sb

Preflight → geração única

  1. Tags viram perguntas; blocos viram opções.
  2. preflight_preparar congela a seleção.
  3. Usuário aprova de modo inequívoco.
  4. preflight_confirmar aprova e inicia uma geração usando o snapshot.
  5. Backend cria a idempotência.

Banco-only permanece obrigatório.

/vibelaw

Preflight → job duplo

  1. Complementos e blocos-base entram no snapshot.
  2. preflight_preparar valida as âncoras internamente.
  3. HTML mostra o diff e os textos em negrito.
  4. preflight_confirmar cria um job coordenado.
  5. Backend gera FIEL e depois VIBELAW.

O GPT não faz duas chamadas e não monta chaves com hash.

Roadmap de implementação

Execução reversível em cinco waves, sem big bang.

W0 · Congelar e provar o bug

Salvar 3 conversas que falharam; registrar tool trace; medir onde parou; criar golden tests para /peticao, /sb e /vibelaw. Nenhuma mudança em produção.

W1 · Backend v2 paralelo

Criar RPCs v2 e contrato por preflight_id; manter tabela/coluna/hash atuais. Alterar sb-externo para aceitar v1 e v2. Testar stale version, bloqueios, âncoras e idempotência.

W2 · MCP simplificado

Adicionar as duas tools novas; anexar UI ao preflight_preparar; remover gate de report_url; implementar conteúdo de fallback. Tools antigas permanecem disponíveis só no perfil de teste.

W3 · KB v2.3 enxuta

Atualizar instructions, Kernel, preflight e as três skills. Rodar busca global por selection_hash, preflight_exibir, report_url e PREFLIGHT_HTML_AUSENTE. Regenerar manifesto.

W4 · Canário real e virada

2 advogados, 10 casos, conversa nova e conversa longa. Critério: zero bloqueio por UI/hash, 100% das gerações saem do snapshot aprovado, nenhuma geração antes da ordem humana.

W5 · Limpeza pós-aceite

Ocultar tools v1 do GPT, preservar compatibilidade Claude/MdFlow, documentar rollback e decidir depois se a coluna de hash continua para auditoria. Recomendo mantê-la.

7

Plano de testes e observabilidade

O projeto só está corrigido quando o fluxo humano passar, não quando o deploy responder 200.

Golden E2E obrigatório

  • HTML abre: usuário aprova e segue.
  • HTML não abre: fallback completo aparece e o fluxo segue.
  • Usuário altera um bloco: nasce v+1; v1 não aprova.
  • Usuário diz apenas “ok” na rodada de decisões: não gera.
  • Usuário diz “aprovar e gerar”: uma confirmação, uma execução.
  • VibeLaw com âncora inválida: bloqueia antes da aprovação.
  • VibeLaw válido: FIEL antes da VL, sem duas calls do GPT.
  • Repetição da confirmação: idempotente.

Telemetria mínima

  • preflight_id, modo, versão e status.
  • presentation_mode=mcp_app|text_fallback.
  • tempo preparar → aprovação → geração.
  • motivo de bloqueio normalizado.
  • versão da KB e do servidor MCP.
  • zero conteúdo jurídico sensível nos logs.
  • correlation ID único por fluxo.
  • dashboard com taxa de sucesso por modo.

Rollout e rollback

Compatibilidade dupla até o canário provar o v2.

Rollout
  1. Publicar RPCs/tools v2 sem remover v1.
  2. Feature flag por token/perfil GPT piloto.
  3. Executar golden set e canário humano.
  4. Virar somente o perfil Jurídico GPT.
  5. Depois alinhar Claude e frontend, se aprovado.
Rollback
  1. Desligar flag PREFLIGHT_V2.
  2. Reexpor tools v1 no allowlist.
  3. Manter linhas v2 como auditoria; sem delete.
  4. Reverter KB para pacote anterior.
  5. Nenhum rollback de dados é necessário.
Regra de segurança: não remover migrations, colunas ou RPCs v1 durante o canário. A simplificação é primeiro de contrato público; a limpeza física só ocorre depois de evidência real.
9

Definição de pronto e veredito final

O que precisa estar verdadeiro antes de declarar o problema resolvido.

DoD
  • Usuário nunca vê nem copia hash.
  • HTML permanece o preflight principal.
  • Falha do iframe não impede aprovação.
  • Uma versão antiga nunca pode ser aprovada.
  • Geração usa apenas snapshot do backend.
  • /peticao, /sb e /vibelaw passam no canário.
  • KB não contém regras contraditórias.
  • Rollback por flag comprovado.
Veredito

GO para o redesenho v2

Não recomendo eliminar a hash do banco. Recomendo eliminá-la completamente da experiência e dos parâmetros usados pelo GPT.

Não recomendo HTML bruto gerado pelo modelo. Recomendo MCP App como apresentação principal, com fallback equivalente e não bloqueante.

A correção definitiva exige MCP + backend + KB. Mexer em apenas uma camada vai repetir o ciclo de falhas.

Decisão proposta ao CTO: aprovar a arquitetura C e executar W0–W4. O sistema deixa de depender de “o GPT lembrar a hash” e de “o iframe provar que abriu”, mas mantém o que realmente importa: versão imutável, conferência humana e geração fiel ao snapshot aprovado.
10

Base oficial considerada

Limites reais da integração com o ChatGPT.

A documentação oficial define a UI MCP como opcional, executada em iframe, e recomenda que as ferramentas continuem úteis sem o componente. Também recomenda separar processamento de dados e apresentação, mantendo os dados de negócio no servidor.
