Sumário executivo

O motor de geração de petição (front → webhook n8n → Apps Script → Google Docs) está funcional — geração testada de ponta a ponta com substituição correta de campos e blocos. Os problemas concentram-se em: (1) segurança de banco (RLS aberto), (2) blocos não selecionados que vazam como {{tag}} no documento final, (3) dívida técnica de triggers redundantes e pipelines n8n órfãos. O erro de vínculo de empresa relatado não está no banco — precisa da mensagem de erro da tela para fechar.

Fase 1 — Backend (Supabase)

P0  RLS totalmente aberto (segurança / LGPD)
As tabelas processos e empresas têm uma única policy allow_all com USING (true) e WITH CHECK (true) para os papéis anon, authenticated, public.
  • Qualquer um com a anon key (exposta no front) lê e escreve todos os processos — incluindo CPF, dados do cliente, valores.
  • Nomes das policies — allow_all_temporary_dev e allow_all_emergency_policy — indicam que foram medidas temporárias que ficaram em produção.
  • Fix: definir policies reais por papel/organização. Como o sistema antigo é mono-tenant (Midas), no mínimo restringir escrita a authenticated e bloquear anon.
P1  Triggers redundantes em processos (25 triggers!)
Vários triggers fazem a mesma coisa, aumentando risco de efeito colateral e custo por escrita:
RedundânciaTriggersFunção
Sync advogado (duplicado exato)trg_a1_processos_sync_advogado + trg_sync_advogado_columns_processosambos executam sync_advogado_columns_processos()
Sync empresa (sobreposto)trg_sync_processos_empresa + trg_sync_processos_id_empresatrg_sync_processos_empresa() e sync_processos_id_empresa() — mesma finalidade (resolver id↔nome)
Populate advogado/OABtrg_a2_processos_populate_oab, trg_processos_advogado_codigo, trg_populate_processo_advogado3 triggers sobre advogado/OAB
Fix: consolidar os pares duplicados num único trigger; manter um só responsável por empresa e um só por advogado.
OK  Erro de vínculo de empresa — banco descartado
RLS é allow_all (não bloqueia); resolve_empresa_id_by_nome() e os triggers de sync usam LIMIT 1/condicionais (não falham com nomes duplicados); UPDATE manual de empresa_re/id_empresa funciona. O erro está no front (Lovable) ou no fluxo de UI — pendente a mensagem de erro exata da tela para fechar.

Fase 2 — n8n (workflow de geração)

Webhook único: POST /webhook/mdflow/modelos/gerador (header mdflow: MdL1501@).

P1  Blocos não selecionados vazam como {{tag}} no documento final
O Apps Script substitui apenas os placeholders enviados; tags de blocos opcionais não escolhidos não são removidas. Exemplo real (apelação gerada): sobraram {{divergencia_fatura}}, {{provas_unilaterais}}, {{audio_parte_autora}}, {{conversa_interna_chat}} crus na peça.
Fix: no Apps Script, após as substituições, rodar um replaceText("\\{\\{[a-z_0-9]+\\}\\}", "") final para limpar placeholders remanescentes (ou enviar todas as tags do modelo com valor vazio quando não selecionadas).
P1  2 pipelines órfãos no workflow
O switch tipo_acao roteia tanto orgao quanto empresa para o mesmo Pipeline 1 (:Advogados → … → Edit Fields → Preparar para script1 → HTTP Request). Os Pipelines 2 (:Advogados1, SmartBlocks/IA) e 3 (:Advogados2, empresa) não têm conexão de entrada — estão mortos.
  • A spec descrevia o Pipeline 3 como "principal", mas na prática tudo passa pelo Pipeline 1 hoje.
  • Fix: remover Pipelines 2/3 (ou reconectar conscientemente). Manter 3 cópias de Edit Fields obriga a editar em triplicata (foi onde adicionei uf/data — só no Pipeline 1, que é o ativo).
CORRIGIDO  Campos {{uf}} e {{data}}
O nó Edit Fields só gerava estado_extenso (capitalizado) e data_hoje; o modelo de contrarrazões usa {{uf}} (maiúsculo) e {{data}}. Adicionei os dois campos: uf = nome do estado em MAIÚSCULAS (RS→RIO GRANDE DO SUL); data = igual data_hoje. Geração testada — substituiu corretamente.
P2  {{uf}} usa processos.estado, endereçamento usa outra fonte
Se o campo estado do processo divergir do CNJ (visto no teste: CNJ de SP, estado=RS), o tribunal no corpo ({{uf}}) e o endereçamento do cabeçalho saem diferentes. Fix: validar estado contra o TR do CNJ no cadastro do processo.

Fase 3 — Front (página OlivIA petições)

P2  Análise limitada — código não disponível localmente
O front antigo é um projeto Lovable separado (c8f8b829), sem código-fonte neste ambiente. Análise feita via bundle minificado + runtime. Além disso, a automação headless não consegue logar (o botão "Entrar" não dispara o signInWithPassword — provável handler que não responde a clique sintético), o que impede teste visual automatizado dos steps.

O que foi possível confirmar

  • O front faz uma única chamada externa: o webhook de geração. Cadastro/edição de processo e vínculo de empresa são escrita direta no Supabase (sem n8n) — passando pelos 25 triggers.
  • Implicação: o "erro ao cadastrar empresa no processo" é, ou (a) validação/estado no React, ou (b) um dos triggers BEFORE INSERT/UPDATE falhando no insert/update direto. Para isolar, preciso da mensagem de erro exata (toast/console).
  • Fluxo de geração (steps): seleciona processo → tipo de petição → categoria (ex.: Mercado Livre) → modelo (filtrado por categoria+versão) → blocos por tag → gera. Confirmado funcional ponta-a-ponta.

Relação Página ↔ Processos ↔ Cadastro

Dependências confirmadas para a petição sair correta:

  • processos.estado → alimenta {{uf}} / {{estado_extenso}} / endereçamento.
  • processos.empresa_re + id_empresa → {{empresa_re}} (ré/apelada). 848 processos sem isso.
  • processos.id_cliente → dados do autor, CPF, qualificação de gênero.
  • processos.id_advogado → nome, OAB, endereçamento, rodapé (5 triggers tratam isso).
  • Categoria da empresa (empresas.categoria_id) deve casar com olivia_modelos_peticao.categorias_empresa_ids para o modelo aparecer. As entradas "Mercado Pago" estão com categoria_id = null — não associadas à categoria Mercado Livre.
