Outros Problemas Identificados

P0 BUG-1
Campos flat não populados pelo Worker C
Worker C grava tudo em analise_ia JSONB mas não popula os campos flat urgencia, tipo_acao, ia_acao_recomendada. Resultado: filtros do /controller não funcionam, badges de urgência não aparecem.
P1 BUG-2
Polo detection frágil — maioria retorna "desconhecido"
Worker A extrai polo via CSS class (.infraTable tr.autor). A maioria dos eventos retorna polo="desconhecido", impedindo o Worker C de filtrar petições do nosso escritório vs réu.
P1 BUG-3
urgencia mapeamento incorreto — JSONB "A" vs campo DB "imediata"
Worker C salva urgencia: "A" no JSONB mas o banco espera 'imediata' | 'alta' | 'normal' | 'informativa'. Frontend patchado para ler do JSONB mas campo DB continua null — ordenação e filtros por urgência quebrados.
P1 BUG-4
Playwright document download implementado mas 0% funcional
P0-02 foi implementado mas 0 de 26 documentos com URL foram baixados. Hipóteses: timeout aguardando PDF, redirect para viewer externo, sessão expirada no momento do download, formato de URL incompatível com page.goto.
P1 BUG-5
Evento #22003 anômalo — numeração global EPROC vs por processo
Processo 5009872-88: evento #22003 vs sequência histórica máxima #177. EPROC às vezes retorna numeração de evento do sistema global. Worker C detecta e classifica corretamente como movimento_em_duvida. Necessita normalização no Worker A.

Arquitetura Proposta: Fluxo 2-Pass Detalhado

Princípio central: o Worker A é o único com sessão autenticada no EPROC. O Worker C deve sinalizar quais documentos precisa, e o Worker A os busca antes da análise definitiva. Dois passes de IA, dois passes de Playwright.

1

Worker A — Pass 1: Navegar e Capturar

Acessa o processo no EPROC via Playwright. Captura screenshot da tela + HTML completo da tabela de eventos. Extrai lista de eventos com títulos, datas, URLs de documentos e polo das partes (lendo texto "AUTOR"/"RÉU" nos TDs, não apenas classes CSS). Armazena em cecilia_movimentacoes_brutas com fase A1_captura.

movimentacoes_brutas (sem documento_raw) screenshot_base64 polo_detectado (melhorado)
Enfileira job fase C1_triagem para Worker C
2

Worker C — Pass 1: Triagem Rápida

Recebe eventos SEM documentos. Classifica o óbvio com alta confiança: historico (ruído, rotina sem ação) finaliza imediatamente. Para eventos que requerem documento — emite lista estruturada de URLs necessárias. NÃO gera movimento_em_duvida por falta de doc — escala para Pass 2.

intimacoes tipo:historico (finais) documentos_necessarios: [{url, evento_num, motivo}] job.fase = A2_fetch_doc
Worker A monitora jobs com documentos_necessarios não vazios
3

Worker A — Pass 2: Fetch Documentos Autenticado

Recebe lista de URLs sinalizadas pelo Worker C. Para cada URL: usa sessão Playwright autenticada para abrir o documento (page.goto + aguardar load completo). Extrai texto via page.evaluate ou captura PDF. Atualiza documento_raw em cecilia_movimentacoes_brutas. Enfileira job para fase C2.

documento_raw populado url_fetch_status: ok/fail job.fase = C2_analise_profunda
Worker C processa jobs na fase C2 após Worker A completar fetch
4

Worker C — Pass 2: Análise Profunda

Recebe eventos COM documento_raw preenchido. Lê texto completo: dispositivo, comando, prazo, parte intimada. Gera intimação de alta confiança com todos os campos flat populados: urgencia mapeada (A→imediata, B→alta, C→normal, D-G→informativa), tipo_acao, ia_acao_recomendada. Confiança esperada >85%.

intimacoes com alta confiança campos flat populados urgencia mapeada corretamente
Schema — Novo campo necessário
-- cecilia_jobs: novo campo para lista de documentos necessários ALTER TABLE cecilia_jobs ADD COLUMN IF NOT EXISTS documentos_necessarios JSONB; -- formato esperado: -- [{"url": "https://eproc...", "evento_num": 42, "motivo": "decisao — precisa ler dispositivo"}] -- cecilia_movimentacoes_brutas: status do fetch de cada URL ALTER TABLE cecilia_movimentacoes_brutas ADD COLUMN IF NOT EXISTS url_fetch_status TEXT; -- valores: null = não tentou | 'ok' | 'fail' | 'no_url'

Playbooks do João — Validação de Alinhamento

PB3 — Evento de Referência

"A Cecília deve sempre abrir o evento de referência quando a intimação indicar 'Refer. ao Evento X'" — o fluxo 2-pass atende diretamente: quando Worker C identifica referência a evento anterior, inclui a URL do evento original em documentos_necessarios para o Worker A buscar na sessão autenticada.

PB6 — Documento Vinculado

"Quando houver documento vinculado, a Cecília deve abrir o documento e ler o conteúdo necessário, especialmente dispositivo, comando, prazo, parte intimada" — exatamente o que o Worker C Pass 2 fará com documento_raw. Dispositivo, comando e prazo são campos de extração obrigatória no prompt do Pass 2.

PB6 — Fluxo-Mãe

"navegar → abrir evento → abrir documento → classificar → voltar à fila" — o fluxo 2-pass é a implementação direta deste playbook. O Fluxo-Mãe do João é, literalmente, a arquitetura que estamos propondo. A validação é completa: os playbooks definem o comportamento correto que o 2-pass realiza.
