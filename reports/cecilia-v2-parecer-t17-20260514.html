Qualidade das Análises — Amostras Reais
SDK Agent Sonnet 4.6

⭐ A qualidade das análises é excelente

O SDK Agent demonstrou raciocínio jurídico sofisticado. Nos 4 processos concluídos, identificou corretamente: prazos decorridos que exigem SISBAJUD, ausência de citação que exige providência alternativa, trânsito em julgado que gera cumprimento de sentença, e revelia. Em todos os casos aplicou os playbooks PB1-PB7 com precisão, usou o Atlas RAG para buscar casos similares, e sinalizou quando o documento estava inacessível em vez de inferir erroneamente.

Bugs Encontrados e Corrigidos no Piloto
7 bugs · todos corrigidos
FIX-01

Construtor BaseAdapter com parâmetros errados

Worker A instanciava new AdapterClass({ page, config: { hostBase: url } }) em vez de { page, logger, oab }. O Adapter jogava erro silencioso, nenhum processo era navegado.

FIX-02

Colunas de schema incorretas no SELECT do Worker A

SELECT usava ultimo_evento_id, juiz, vara, comarca — colunas que não existem. Schema real: ultimo_evento_eproc, vara_distribuicao, tribunal_id. PostgREST retornava erro fazendo a navegação falhar.

FIX-03

ON CONFLICT por eventos duplicados no EPROC

Tabela #tblEventos do EPROC retorna linhas duplicadas para alguns eventos. O upsert falhava com "cannot affect row a second time". Corrigido com deduplicação via new Map(eventos.map(e => [e.numero, e])).

FIX-04

path null no Worker C — campo tribunal não preenchido

Worker A não populava tribunal na tabela cecilia_movimentacoes_brutas. Worker C chamava readProcessFile(cnj, null) e quebrava com TypeError. Corrigido em Worker A (adicionar campo) + Worker C (fallback || 'TJRS').

FIX-05

tipo_saida check constraint violation

SDK Agent retornava tipos não homologados como "ruido", "aguardar". A RPC fn_intimacao_insert_validated rejeitava. Corrigido com sanitizarTipoSaida() que converte inválidos para movimento_em_duvida, e prompt atualizado com os 8 tipos válidos.

FIX-06

Status inicial inválido em cecilia_xls_uploads

Trigger do banco só aceita processando | concluido | erro. Script de trigger usava pendente. Corrigido no script de upload.

PENDENTE

Logger com argumentos invertidos (cosmético)

Todos os log.error({data}, 'message') no Worker A deveriam ser log.error('message', {data}). Resultado: stdout mostra [object Object] "mensagem". Não quebra a lógica, mas dificulta debugging.

Gargalos Críticos de Arquitetura

🐌 Throughput do Worker A é o maior problema

1 processo a cada ~2 minutos. O bottleneck é o login SSO+2FA do EPROC que leva ~50-60 segundos POR PROCESSO — porque o Worker A faz login novo em cada item da fila. Com 5.800 processos Midas e um único Worker A sequencial: 5.800 × 2min = ~193 horas = ~8 dias para processar um ciclo completo. Isso é inaceitável para monitoramento processual diário.

⚠ 29% de movimento_em_duvida — documentos inacessíveis

O Worker C usa fetch_document(url) via HTTP GET para ler documentos. Mas a maioria dos documentos no EPROC exige sessão Playwright ativa com cookie de autenticação válido. Resultado: o SDK Agent recebe a URL do evento mas não consegue ler o conteúdo, e classifica como movimento_em_duvida. O Worker A navega com Playwright mas não baixa o conteúdo dos documentos durante a navegação — deixa para o Worker C tentar depois, quando já não tem sessão ativa.

⚠ Marco zero: processando histórico inteiro na primeira rodada

Um processo de 2022 com 107 movimentos vai chamar o SDK Agent 107 vezes na primeira execução. Isso é caro e lento. Na segunda rodada o ultimo_evento_eproc já estará populado e o Worker A vai extrair apenas os eventos novos — mas a primeira vez é problemática para processos antigos com histórico grande.

Vai Funcionar na Prática?

⚠ Sim — mas só após resolver o throughput do Worker A

A Cecília v2 funciona. A qualidade das análises é excepcional. A triagem inline é correta. O SDK Agent aplica os playbooks com precisão e sabe quando não classificar (zona cinzenta). O piloto de 20 processos rodou end-to-end sem intervenção humana após os bugs serem corrigidos.

O que já funciona em produção
  • Login SSO + 2FA EPROC (4 OABs RS/SC)
  • Extração de eventos via Playwright
  • Triagem inline (36 regras regex)
  • SDK Agent com playbooks PB1-PB7
  • Prompt cache (-30-50% custo IA)
  • Contexto 3 camadas (thread+snapshot+Obsidian)
  • fn_intimacao_insert_validated funcional
  • LaunchAgents resilientes (KeepAlive)
O que bloqueia adoção total
  • Throughput: 1 proc/2min → precisa paralelismo
  • 29% sem doc: fetch_document falha sem sessão
  • Marco zero: histórico inteiro na 1ª rodada
  • TJSP: 35% do portfólio fora
  • custo_ia null: custo real desconhecido
  • Logger invertido: debugging difícil
🔴
P0 — Críticos (para funcionar em produção)
1

Worker A paralelo — reusar sessão por OAB

Em vez de fazer login novo em cada processo, manter a sessão Playwright ativa por OAB e processar todos os processos daquela OAB sem novo login. Com 4 OABs em paralelo (RS116571, RS131163, SC074025, SC075466), o throughput salta de 1 para ~4 processos/min — ciclo completo de 5.800 processos em ~24h em vez de ~8 dias.

Impacto: throughput 4× → viabiliza ciclo diário real · Estimativa: 1-2 dias de implementação
2

Worker A baixa conteúdo do documento durante navegação

Hoje o Worker A extrai apenas o título e número do evento, deixando a URL para o Worker C tentar depois via HTTP. O problema: documentos EPROC exigem sessão ativa. Solução: durante a navegação Playwright (quando a sessão já está ativa), o Worker A deve clicar no link do documento e capturar o HTML/texto, salvando em cecilia_movimentacoes_brutas.documento_raw. Isso elimina os 29% de movimento_em_duvida por documento inacessível.

Impacto: 29% de movimento_em_duvida → menos de 5% · Qualidade das análises sobe muito · Estimativa: 2-3 dias
3

Marco zero inteligente — data de corte por processo

Na primeira rodada, limitar o Worker A para processar apenas os últimos 30 eventos (ou eventos após uma data configurável, ex: 90 dias atrás). Processos de 2018 com 62 eventos históricos não precisam de análise do SDK Agent em 62 chamadas — apenas os eventos recentes importam. Adicionar um parâmetro data_corte_historico na tabela cecilia_processos_fila que o Worker A respeita.

Impacto: reduz jobs Worker C em ~60-70% na primeira rodada · Custo IA cai proporcionalmente · Estimativa: 1 dia
4

Registrar custo_ia em todas as intimações

O Worker C usa o SDK Agent mas não popula intimacoes.custo_ia e intimacoes.tokens_ia. O Anthropic SDK retorna usage na resposta. Simples: capturar response.usage e calcular custo com a fórmula de preço do Sonnet 4.6 ($3/1M input, $15/1M output). Sem isso não há visibilidade de custo real.

Impacto: visibilidade total de custo · Permite decidir se usar Haiku para triagem leve · Estimativa: meio dia

P1 — Importantes
5

Regras de triagem para "publicação DJ sem documento"

29% das intimações são movimento_em_duvida por documento inacessível. Muitos desses são eventos do tipo "PUBLICADO NO DJ ELETRÔNICO — REFER. AO EVENTO: X" onde o Evento X não está disponível. Com uma regra de triagem que detecte esse padrão e marque como movimento_em_duvida direto (sem chamar o SDK Agent), economizamos ~20% das chamadas à IA.

Impacto: ~20% de redução de custo IA · Estimativa: meio dia para adicionar regras
6

Dashboard de saúde da Cecília em /controller

Hoje para saber o estado da Cecília é preciso fazer queries SQL. Implementar uma aba na página /controller/cecilia mostrando: fila pendente, última execução Worker A/C, taxa de ruído vs relevante, intimações geradas hoje, custo acumulado, status dos LaunchAgents. A tabela cecilia_health já existe mas está subutilizada.

Impacto: operação sem precisar do Jarbas para monitorar · Estimativa: 2-3 dias
7

Correções do logger no Worker A

Todos os log.error({obj}, 'mensagem') estão com argumentos invertidos, gerando [object Object] "mensagem" em todos os logs. Corrigir para log.error('mensagem', {obj}) em ~20 ocorrências no Worker A. Simples mas importante para debugging em produção.

Impacto: logs legíveis para debugging operacional · Estimativa: 1 hora
8

Alerta WhatsApp/Telegram para atividades urgência A

Quando o Worker C gera uma intimação tipo_saida = 'atividade' com urgência A, enviar notificação imediata via WhatsApp (MdZap) ou Telegram para o advogado responsável. Hoje as atividades ficam na tabela mas ninguém é notificado automaticamente. Um trigger no banco ou um n8n cron de 5 minutos verificando novas atividades urgentes resolveria.

Impacto: nenhum prazo urgente perdido · Estimativa: 1 dia (n8n + MdZap)
9

XLS upload via interface MdFlow (sem script manual)

Hoje o processo de upload exige: (1) subir XLS para o bucket Supabase, (2) criar registro em cecilia_xls_uploads, (3) chamar a Edge Function. Tudo via script. Implementar um componente de upload na aba Cecília do Controller com drag-and-drop, seleção de data range, e feedback em tempo real do processamento via polling.

Impacto: Heloísa/João podem disparar a Cecília sem Jarbas · Estimativa: 1-2 dias

P2 — Visão de Longo Prazo
10

TJSP — suporte ao e-SAJ

Aproximadamente 35% do portfólio Midas está em SP. O e-SAJ tem arquitetura diferente do EPROC mas também é navegável por Playwright. Criar um TJSPAdapter análogo ao TJRSAdapter. A maior diferença é a ausência de TOTP — login é mais simples, mas a estrutura das páginas de processo é diferente.

Impacto: cobertura total do portfólio Midas · Estimativa: 1-2 semanas
11

Feedback loop — advogado treina a triagem

Quando um advogado reclassifica uma intimação no Controller (ex: de historico para atividade ou vice-versa), capturar esse feedback e usar para melhorar as regras de triagem. Pode ser simples: um botão "Classificação incorreta" que insere na tabela cecilia_triagem_feedback e periodicamente o Jarbas consolida em novas regras regex.

Impacto: sistema melhora com uso · Redução de zona_cinzenta ao longo do tempo · Estimativa: 1 semana
12

Ciência e renuncia automática (flag_ciencia_renuncia)

A tabela intimacoes já tem flag_ciencia_renuncia. Quando o SDK Agent identifica que um evento é uma intimação de ciência (ex: sentença desfavorável que exige apenas registro), e o advogado configurou auto_aprovar = true para esse tipo, a Cecília poderia executar a ciência via Playwright automaticamente — sem intervenção humana.

Impacto: elimina trabalho repetitivo de ciência em centenas de processos · Estimativa: 2-3 semanas (inclui testes extensivos)
13

2 modelos: Haiku para triagem, Sonnet para análise profunda

Hoje todos os eventos não-ruído vão para Sonnet 4.6 (~20x mais caro que Haiku). Para eventos com baixa complexidade (ex: "JUNTADA DE PETIÇÃO" sem documento disponível), um Haiku poderia fazer triagem leve e devolver a classificação mais barata. Sonnet só seria chamado para eventos com documento disponível ou alta complexidade. Estimativa de economia: 40-60% do custo IA.

Impacto: redução de custo de 40-60% · Estimativa: 1 semana
14

Integração Datajud — enriquecer sem EPROC

Para processos onde o Worker A falhou (browser crash, timeout), usar a API do Datajud (pública e gratuita) para obter os últimos movimentos. Não tem a mesma fidelidade do EPROC mas permite continuidade quando o Playwright falha. Datajud já foi avaliado na D5 da arquitetura v5 — foi descartado como fonte primária mas pode ser excelente como fallback.

Impacto: resiliência para falhas do Playwright · Zero custo adicional · Estimativa: 3-5 dias

Resumo Executivo
Meu parecer como CTO que rodou o piloto

A Cecília v2 é o maior avanço técnico do Midas nos últimos 12 meses. A qualidade das análises jurídicas é genuinamente impressionante — detectou decurso de prazo executivo, trânsito em julgado, ausência de citação, e revelia com raciocínio coerente e referência precisa aos playbooks. Nenhum sistema de mercado entrega isso neste nível de profundidade.


Substitui a Judit? Sim — e economiza R$7.557/mês. A Judit era uma API de extração. A Cecília é um paralegal automatizado. O gap de qualidade é imenso.


Está pronta para produção com 5.800 processos? Ainda não. O problema crítico é o throughput — 1 processo/2min significa um ciclo completo em 8 dias. Isso não serve para monitoramento diário. O fix é arquitetural mas não complexo: reusar sessão Playwright por OAB (P0-01). Com isso o ciclo cai para ~24h, que já é aceitável. Depois disso, corrigir o fetch_document (P0-02) eliminará os 29% de movimento_em_duvida e a qualidade ficará excelente.


Minha recomendação: 1 sprint de 1 semana focado nos 4 P0s (sessão reutilizada + download de documentos + marco zero + custo_ia). Depois lançar em produção com os processos do RS/SC. TJSP fica para um sprint futuro.
